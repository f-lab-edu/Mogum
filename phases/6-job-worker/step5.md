## 배경

step 4 의 한 바퀴(`runOnce` 등)를 **워커 `N` 개의 스레드**로 돌리고, 서버가 켜질 때 시작하고 꺼질 때(배포) 정상적으로 멈추게 한다. 서버 프로세스 하나가 API 와 워커를 함께 돌린다(`AGENTS.md` 운영 줄).

**계약 문서는 이 phase 전에 정해 커밋했다. 코드가 계약과 어긋나면 코드를 계약에 맞추고, 맞출 수 없으면 `blocked` 로 멈춰라. 계약 문장을 고치지 마라.**

## 작업

### 1. 워커 돌리기 — `worker` · 빈 등록은 `config`

- 워커 수 `N` 은 설정 한 곳의 **임시 값**이다(04 §10 · ADR-105). 0 이면 워커를 띄우지 않는다 — API 만 도는 서버가 된다.
- 워커마다 스레드 하나(플랫폼 스레드)가 「빈손이면 하나를 집어 끝까지 처리 → 없으면 정한 간격을 쉬고 다시」를 돈다(금지 8 — 한 번에 하나).
- 서버 역할(`app.role`)은 만들지 않는다 — 워커 수 0 으로 대신한다. `ArchitectureTest` 의 위 주석과 `docs/04-jobs-and-cost.md` §2.1 의 `config/` 줄(「역할별 빈 등록」)이 이와 다르면 실제로 한 대로 고친다(이 두 곳만 — 규칙은 그대로다).
- **루프는 죽지 않는다** — 한 바퀴 밖으로 나온 예외(DB 연결 끊김 등)는 잡아서 `ERROR` 로 남기고 쉬었다 다시 돈다. 같은 실패가 이어지면 스택은 첫 번째만 찍는다(금지 26 — 1초마다 스택이면 몇 시간 안에 보관 상한을 채운다).
- 쉬는 간격도 설정의 임시 값이다.

### 2. 정상 종료(04 §4.5 · ADR-126)

서버가 꺼지기 시작하면:

1. 새 작업을 꺼내지 않는다.
2. 진행 중인 시도가 결과를 저장하기를 **정한 한도까지** 기다린다 — 기다리는 동안 시한은 그대로 늘린다.
3. 한도를 넘기면 들고 있던 작업을 **기다림으로 돌려놓는다** — `QUEUED` · `lease_until` 비움. 쓰기는 같은 `claim_count` · `RUNNING` 조건이다(금지 9). 돌려놓은 뒤 늦게 끝난 그 시도는 step 4 의 확인으로 아무것도 쓰지 않는다. 크레딧은 그대로다(아직 끝나지 않은 작업이다).

- **한도는 130초(`timeout-per-shutdown-phase`)와 150초(`stop_grace_period`)보다 짧게** 둔다 — 넘으면 기다리는 도중 강제로 죽어 시한으로 되찾는 길로 떨어진다(04 §4.5). 돌려놓기 · DB 처리까지 그 안에 끝나야 한다.
- Spring 의 종료 단계에서 워커가 **DB 연결 풀이 닫히기 전에** 멈추는지 확인해서 정한다(예: `SmartLifecycle` 의 단계). 확인하지 않은 순서를 가정하지 마라.
- 배포는 지금처럼 끄고 켠다(`deploy/deploy.sh`) — 옛 서버와 새 서버를 겹치는 장치를 만들지 마라. 겹쳐도 구조가 그대로인 것은 DB 의 꺼내기 · 시한이 지킨다(04 §3).

### 3. 시한 식(금지 10)

- 04 §10 에 **시한 > 한 시도가 걸릴 수 있는 가장 긴 시간** 의 식을 적는다 — 호출 시간 제한(강의 목록 TASK 가 정한다) · 이어 쓰기 · 자동 다시 시도 횟수 × 간격 · DB 처리를 더한다. 지금 있는 값(시한 · 늘리는 간격 · 다시 시도 횟수 · 간격 · 종료 한도 · 워커 수 · 쉬는 간격)을 설정 이름과 임시 값으로 함께 적는다.
- 지금 있는 값으로 계산되는 부분(예: 늘리는 간격 < 시한, 종료 한도 < 130초)은 설정 검증으로 묶어 값을 잘못 바꾸면 기동이 거부되거나 테스트가 깨지게 한다 — 고른 방법을 04 §10 에 적는다.

### 4. 테스트에서 워커

- **기본 테스트 컨텍스트에서는 워커가 스스로 돌지 않는다.** 돌면 다른 테스트가 만든 작업을 집어 결과가 흔들린다. 공용 테스트 설정에서 워커 수를 0 으로 둔다. 워커 시험은 step 4 처럼 한 바퀴를 직접 부르거나, 이 step 의 시작 · 종료를 테스트가 직접 다룬다. 클래스마다 새 컨텍스트를 띄우는 설정을 늘리지 마라(TEST_GUIDE §5).

### 5. 로그 줄

| 수준 | 언제 | 줄 |
|---|---|---|
| `INFO` | 정상 종료 한도를 넘겨 작업을 기다림으로 돌려놓았을 때 | `job released` (MDC `jobId` · `userId`) |
| `ERROR` | 워커 루프가 한 바퀴 밖에서 예외를 받았을 때 — 이어지면 스택은 첫 번째만 | `worker poll failed` |

정한 줄을 04 §9.1 표 아래에 적는다(테스트가 실제로 찍은 줄을 옮긴다).

### 6. 테스트

- **정상 종료**(07 §1) — 오래 걸리는 스텁으로 작업을 쥔 채 멈추기 시작하면: 한도 안에 스텁을 풀어 주면 결과를 저장하고 `SUCCEEDED` · 멈추기 시작한 뒤에는 새 작업을 꺼내지 않는다 · 한도를 넘기면 작업이 `QUEUED` · `lease_until` 비움이 되고 `job released` 가 찍히며, 그 뒤 풀린 옛 시도는 아무것도 쓰지 않는다. 한도는 테스트에서 짧게 둔다.
- **루프** — 한 바퀴가 예외를 던져도 루프가 살아 다음 작업을 집는다 · 같은 예외가 이어지면 스택이 한 번만 찍힌다.
- **워커 수** — `N` 개가 동시에 서로 다른 작업을 처리한다 · 0 이면 아무것도 집지 않는다.
- **설정 검증** — §3 의 묶음이 깨진 값을 거부한다.
- 기존 테스트가 워커 때문에 흔들리지 않는다 — 전체 `build` 를 돌린다.

### 7. 문서 — 구현으로 정해진 사실만

- `docs/04-jobs-and-cost.md` §10 — 서버마다 워커 수 · 시한 값 · 늘리는 방법 · 정상 종료 한도 · 배포는 끄고 켠다(`deploy/deploy.sh`)를 정한 값으로 옮기고, 시한 식을 적는다. §2.3 — 워커 시작 · 종료. §9.1 — 로그 줄. §2.1 — `config/` 줄(§1 대로).
- `docs/07-testing.md` §4 · §5 — 서버마다 워커 수가 임시 값으로 정해졌음을 적는다.

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 아키텍처 체크리스트를 확인한다:
   - 워커를 참조하는 것이 `config` 뿐인가? `worker` 에 `@Transactional` 이 없는가?
   - 멈추기 시작하면 새로 꺼내지 않고, 한도를 넘기면 같은 `claim_count` · `RUNNING` 조건으로 돌려놓는가?
   - 종료 한도가 130초보다 짧고, 워커가 DB 연결 풀보다 먼저 멈추는가 — 확인한 근거가 있는가?
   - 기본 테스트 컨텍스트에서 워커가 돌지 않는가?
   - 로그 줄이 표의 두 줄뿐이고, 루프 스택이 이어서 찍히지 않는가?
   - `AGENTS.md` 금지 목록 · 작업 방식(TDD)을 위반하지 않았는가?
3. 결과에 따라 `phases/6-job-worker/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`. 담을 것: 시작 · 종료 방식(종료 단계 · 확인한 근거) · 설정 이름과 임시 값 전부 · 시한 식 · 설정 검증 방법 · 테스트에서 워커를 끄는 방법 · 서버 테스트 수(전후)
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 (계약 문서와 코드가 맞지 않음 등) → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- 서버 역할(`app.role`) · 배포 겹치기 · 따로 된 메시지 큐를 만들지 마라. 이유: 워커 수 0 이 API 만 도는 서버를 대신하고, 배포는 끄고 켠다(01 §6 · 금지 5).
- 정해진 때 도는 일(크레딧 채우기)을 만들지 마라. 이유: SCHEDULE §3 상 홈 · 크레딧 TASK 에서 만든다.
- 워커끼리 나누는 메모리 상태(카운터 · 큐 · 잠금)를 두지 마라. 이유: 서버가 여러 대면 쪼개진다(금지 22) — 나누는 것은 DB 의 꺼내기가 한다.
- `deploy/` 의 값(`stop_grace_period`)이나 `timeout-per-shutdown-phase` 를 늘려 한도를 맞추지 마라. 이유: 한도를 그 둘보다 짧게 두는 것이 계약이다(04 §4.5).
- 작업에 적지 않은 운영 로그 줄(`INFO` 이상)을 더하지 마라. 이유: 줄마다 14일 · 500MiB 보관을 나눠 쓰고, DB 에 남는 사실은 DB 에서 본다. 기동 · 종료는 Spring 이 이미 남긴다.
- 계약 문서(04 의 규칙 문장 · ADR · `AGENTS.md` 금지 목록 · README)의 규칙을 고치지 마라. 이유: phase 전에 정해 커밋했다. 어긋나면 `blocked`.
- 커밋하지 마라. 이유: Claude 리뷰가 승인한 뒤 하네스가 커밋한다.
- 기존 테스트를 깨뜨리지 마라
