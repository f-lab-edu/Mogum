## 배경

복습 탭(06 §11)의 두 동작 — **평가 보내기**(4단계 스스로 평가가 FSRS 에 그대로 들어간다 — ADR-015)와 **카드 지우기**(틀린 카드는 사용자가 지운다 — ADR-065)를 만든다.

**계약 문서는 이 phase 전에 정해 커밋했다. 어긋나면 코드를 계약에 맞추고, 맞출 수 없으면 `blocked` 로 멈춰라. 계약 문장을 고치지 마라.**

## 작업

경로 · 칸 이름 · 오류 code 는 지금 API 의 짜임에 맞춰 정하고 05 에 적는다(05 §5). 성공은 `ApiResponse`(본문 없는 성공은 지금 쓰는 `204` 방식을 따른다), 오류는 `ApiException(ErrorCode)`(금지 25). 요청 본문은 `@Valid` 로 검사하고, 모르는 평가 값은 지금의 칸 오류 방식(`FIELD_INVALID` · `INVALID_VALUE`)을 따른다.

### 1. 평가 보내기 — `card` 패키지

- 보내는 것 — 카드 ID · 평가(`AGAIN` · `HARD` · `GOOD` · `EASY` — 02 §8.7 의 이름 그대로).
- **받는 조건** — 주인의 카드 · `ACTIVE` · 학습 완료 뒤(`due_at` 이 있다) · **지금 볼 수 있는 카드**: `REVIEW` 는 `due_at` 이 다음 하루의 시작(새벽 4시) 전, 학습 단계는 `due_at` 이 지금부터 앞당겨 보기 한도(20분 — step 1 의 상수) 안. 그 밖이면 거절 code 하나(새로 정해 05 §1.2 에 한 줄 — 화면은 문구를 보이고 목록을 다시 읽는다). 남의 카드 · 없는 카드 · 학습 완료 전 · 코스 지워짐은 `NOT_FOUND`(금지 18 — 보이지 않는 카드는 없는 것이다).
- 한 트랜잭션에서 — 카드 행을 잠그고(`PESSIMISTIC_WRITE` 등) 받는 조건을 확인한 뒤, step 0 의 `review(card, rating, 지금)` 결과를 `Card` 의 평가 반영 메서드로 적고, `Review.record(card, rating)` 로 복습 기록 한 줄을 남긴다. 「지금」은 `Clock` 에서 한 번 받아 카드의 `last_reviewed_at` 과 계산에 함께 쓴다. 복습 기록의 평가한 때는 `created_at`(JPA Auditing — 같은 `Clock`)이다 — 스트릭이 이 값으로 센다(ADR-178).
- **같은 카드의 평가가 겹치면** 행 잠금으로 차례로 처리한다 — 뒤 요청은 앞 요청이 바꾼 상태를 다시 읽고 받는 조건을 다시 본다. 서버 메모리의 잠금을 쓰지 마라(금지 22). 연타는 화면이 요청 중 버튼을 막는다(step 3) — 서버에 요청 ID 같은 중복 막기 장치를 따로 두지 마라(ADR-102).
- 간격 · 상태는 step 0 계산 그대로 적는다 — 손으로 고치지 마라(금지 21).
- 응답 — 화면은 받은 목록을 이어 보고 다 보면 다시 읽으므로 다음 카드를 돌려줄 필요가 없다. 본문 없는 성공으로 둘지 작은 객체로 둘지 정한다(05 §1 — 넓힐 수 있게).

### 2. 카드 지우기 — `card` 패키지

- 받는 조건 — 1 과 같은 「보이는 카드」(주인 · `ACTIVE` · 학습 완료 뒤). 아니면 `NOT_FOUND`. 오늘 복습할 카드가 아니어도 지울 수 있다.
- 한 트랜잭션에서 02 §8.6 「사용자가 카드를 지울 때」 순서대로 — 그 카드의 `reviews` → `card_concepts` → `cards`. **개념 사전(`concepts`)은 지우지 않는다**(ADR-065 · ADR-049) — 카드가 하나도 붙지 않은 개념도 남는다.
- 같은 카드의 평가와 지우기가 겹쳐도 깨지지 않게 1 과 같은 행 잠금을 먼저 잡는다. 지운 뒤 온 평가는 `NOT_FOUND`.
- 같은 카드를 두 번 지우면 두 번째는 `NOT_FOUND` 다(정하고 05 에 적는다).

### 3. 시험

- 컨트롤러(`@WebMvcTest`) — 경로 · 본문 검사(빠진 평가 · 모르는 평가) · 응답 · 오류.
- 통합(`@IntegrationTest` — 실제 DB · `TestClock`):
    - **같은 날 다시 보기**(07 §1) — 간격은 step 0 의 라이브러리 기본값 그대로다(ADR-164): 처음 배우는 카드(`LEARNING`)에 「다시」를 보내면 첫 단계로 돌아가 1분 뒤 · `GOOD` 이면 다음 단계 10분 뒤 · 복습 중 카드(`REVIEW`)에 「다시」를 보내면 `RELEARNING` 10분 뒤(07 §1 의 「10분 뒤」는 이 경우다). 「다시」를 누른 카드는 그 사이 다른 볼 카드가 없으면 step 1 읽기에 바로 다시 나온다(앞당겨 보기) · 학습 단계를 마치면(`GOOD` 두 번 또는 `EASY`) `REVIEW` 로 날 단위. 기대 간격은 step 0 의 `FsrsCalculatorTest` 가 고정한 값과 같아야 한다 — 다르면 step 문장이 틀린 것이니 `blocked`.
    - 평가가 남기는 것 — 복습 기록 한 줄(평가 · `created_at` = 지금) · 카드 여섯 칸이 step 0 계산과 같다 · 평가 전 읽기에서 보인 그 평가의 간격 == 평가 뒤 `due_at − 지금`(ADR-188) · `updated_at` 이 바뀐다.
    - 거절 — 오늘 볼 카드가 아님(다음 날 새벽 4시 이후의 `REVIEW` · 20분 넘은 학습 단계) · 학습 완료 전 · 코스 지워짐 · 남의 카드 · 없는 카드 — 거절 뒤 카드 · 복습 기록이 그대로다.
    - **같은 카드에 동시에 두 평가** — 둘이 차례로 처리되고, 카드 상태가 두 계산을 차례로 적용한 값과 같거나(둘 다 받은 경우) 뒤 요청이 거절된다(앞 평가로 오늘 볼 카드가 아니게 된 경우). 복습 기록 수가 받은 평가 수와 같다.
    - 지우기 — 카드 · 그 카드의 복습 기록 · 개념 연결이 사라지고 **개념은 남는다** · 같은 강의의 다른 카드 · 다른 카드의 복습 기록은 그대로 · 지운 카드는 step 1 읽기와 코스의 수에서 빠진다 · 두 번째 지우기 · 남의 카드 · 학습 완료 전 카드 `NOT_FOUND`.
    - 지우기와 평가가 동시에 와도 남는 상태가 일관된다(카드가 지워졌거나, 평가가 적용된 카드가 남는다 — 고아 복습 기록이 없다).

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 아키텍처 체크리스트를 확인한다:
   - 평가가 한 트랜잭션에서 카드 잠금 → 조건 확인 → FSRS 반영 → 복습 기록인가? 간격을 손으로 고치지 않는가(금지 21)?
   - 오늘 볼 카드가 아닌 평가 · 보이지 않는 카드 · 남의 카드를 거절하는가?
   - 지우기가 `reviews` → `card_concepts` → `cards` 순서이고 개념을 남기는가?
   - 동시 평가 · 평가와 지우기가 겹쳐도 일관된가? 서버 메모리 잠금이 없는가?
   - `card` 가 `course` 를 참조하지 않는가?
   - `AGENTS.md` 금지 목록 · 작업 방식(TDD)을 위반하지 않았는가?
3. 결과에 따라 `phases/9-card-review/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`. 담을 것: 두 경로 · 요청 본문 · 응답(step 3 화면이 쓴다) · 새 오류 code 와 문구 · 동시 처리 방법 · 서버 테스트 수(전후)
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 (계약 문서와 코드가 맞지 않음 등) → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- 카드 편집 · 직접 추가 · 오류 신고 · 카드별 복습 멈추기 · 카드 다시 만들기 · 평가 되돌리기를 만들지 마라. 이유: 06 §11 「두지 않는 것」(ADR-064 · ADR-065).
- 지운 카드를 숨기기만 하는 상태 값을 더하지 마라. 이유: ADR-155 — 사용자가 지운 카드는 기록까지 지운다(`COURSE_DELETED` 는 코스를 지울 때만이다).
- 개념 사전의 개념을 지우지 마라. 이유: ADR-049 · ADR-065.
- 코스 지우기 · 탈퇴 · 스트릭 · 홈 · 숙련도를 만들지 마라. 이유: SCHEDULE §3 상 12 · 11 · 10 TASK 에서 만든다.
- 작업에 적지 않은 운영 로그 줄(`INFO` 이상)을 더하지 마라. 이유: 줄마다 14일 · 500MiB 보관을 나눠 쓰고, DB 에 남는 사실(복습 기록)은 DB 에서 본다.
- 계약 문서(규칙 문장 · ADR · `AGENTS.md` 금지 목록 · README)의 규칙을 고치지 마라. 이유: phase 전에 정해 커밋했다. 어긋나면 `blocked`.
- 커밋하지 마라. 이유: Claude 리뷰가 승인한 뒤 하네스가 커밋한다.
- 기존 테스트를 깨뜨리지 마라
