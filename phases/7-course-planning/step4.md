## 배경

로드맵의 코스(첫 코스 · 다음 코스)의 강의 목록을 만드는 `PLAN_ROADMAP_COURSE` 의 받기 처리기와 생성 처리기를 짝으로 더한다. 로드맵 화면의 「이대로 시작」(첫 코스)과 「다음 코스 만들기」가 이 받기다.

**계약 문서는 이 phase 전에 정해 커밋했다(`fa5af24`). 어긋나면 코드를 계약에 맞추고, 맞출 수 없으면 `blocked` 로 멈춰라. 계약 문장을 고치지 마라.**

## 작업

### 1. 받기 — 받을 수 있는 때

대상은 `courseId`(짜기 전 코스)다. 주인 확인은 틀이 먼저 한다(남의 것 · 없는 것 · 단일 코스는 `NOT_FOUND` 인지 지금 틀의 동작을 따른다).

- 코스가 **로드맵의 코스이고 짜기 전**(`NOT_PLANNED`)이어야 한다.
- 그 로드맵의 짜기 전 코스 가운데 **순서가 가장 앞선 코스**여야 한다.
- **첫 코스(순서 1)** — 로드맵이 검토 중이면 「이대로 시작」이다: **같은 트랜잭션에서 로드맵을 진행 중으로 바꾼다.** 로드맵이 진행 중이면(첫 코스 만들기가 실패해 버린 뒤 다시) 그대로 받는다. **그 로드맵에 성공하지 않은 로드맵 다시 짜기(`REPLAN_ROADMAP` — 기다림 · 만드는 중 · 실패)가 있으면 받지 않는다**(ADR-182).
- **다음 코스(순서 2부터)** — 로드맵이 진행 중이고 **바로 앞 코스가 다 마침**(`COMPLETED`)이어야 한다(ADR-018). 앞 코스의 카드를 복습했는지는 보지 않는다.
- 받지 않을 때는 아무것도 바꾸지 않는다 — 로드맵 상태 · 작업 · 크레딧 모두(05 §2). 받기 순서상 처리기 확인 뒤에 건 수 · 크레딧에서 거절돼도 트랜잭션 전체가 롤백되어 로드맵 상태가 돌아가는지 시험으로 확인한다.
- 받지 않는 까닭마다 오류 code 를 정해 `ErrorCode` 에 더하고 05 §1.2 의 묶음에 맞춘다(금지 25) — 사용자가 할 일이 다른 만큼만 나눈다(ADR-088). 문구 예: 「앞 코스를 다 마치면 만들 수 있어요」(ADR-171) · 「다시 짜는 중에는 시작할 수 없어요」(ADR-182 — 실패한 다시 짜기는 버리거나 다시 시도해 끝낸 뒤).
- 같은 코스에 같은 받기가 두 번 와도 작업 · 크레딧은 하나다 — 이미 틀이 「같은 대상이면 이미 있는 작업」을 돌려준다(ADR-157). 처리기 확인이 그보다 먼저 돌므로, 두 번째 요청이 확인에서 거절되지 않는지 본다(첫 요청 뒤에도 코스는 아직 짜기 전이다).
- 「진행 중으로 바꾼다」를 처리기 안에서 할지, 틀에 받은 뒤의 자리를 더할지는 정한다. 이름이 「확인」인 메서드가 상태를 바꾸면 그 사실을 인터페이스 주석에 적는다. 상태를 바꾸는 엔티티 메서드를 더한다 — 상태는 앞으로만 간다(02 §2.3).

### 2. 만들기 — 재료

- `generate` 는 트랜잭션 밖이다. 재료는 `TransactionTemplate` 의 읽기 트랜잭션에서 값으로 읽고 트랜잭션을 닫은 뒤 LLM 을 부른다(금지 3 · 4). `generation` 은 `@Transactional` 을 쓰지 않는다.
- 재료(03 §2 · step 2 의 표): 로드맵의 입력(주제 · 목적 · 메모, **수준은 첫 코스만**) · 이 코스의 계획(제목 · 한두 줄 설명 · 다룰 개념) · **바로 앞 코스의 실제 강의 목록**(두 번째부터 — 그보다 앞은 넣지 않는다) · **뒤 코스들의 계획**(앞 코스들의 계획은 넣지 않는다).
- step 2 의 강의 목록 만들기를 쓴다 — 코스 제목은 받지 않는다(계획의 제목 그대로).
- 예외를 던지지 마라 — 실패는 `Failure` 로 돌려준다.

### 3. 저장

- 소유권 확인을 마친 트랜잭션 안이다. 강의들을 만들고(순서 1부터) 코스를 **짜기 전 → 검토 중**으로 바꾼다. 코스 제목 · 계획 칸은 그대로다. `ResultRef` 는 원래 코스 ID 다.
- 코스가 짜기 전이 아니면 불변식 위반이다 — 위 받기 규칙과 로드맵 다시 짜기 규칙(step 5 · ADR-182)이 막는다. 조용히 넘기지 마라.

### 4. 테스트

- 받기 — `@IntegrationTest`(잠금 · 롤백 · 상태가 DB 동작):
    - 첫 코스 받기 → 로드맵 진행 중 · 작업 기다림 · 크레딧 씀.
    - 크레딧 부족 · 건 수 상한으로 거절되면 로드맵이 검토 중 그대로 · 작업 · 크레딧 그대로(07 §1 상태 전환).
    - 성공하지 않은 로드맵 다시 짜기(기다림 · 만드는 중 · 실패 각각)가 있으면 거절 · 아무것도 안 바뀜.
    - 다음 코스 — 앞 코스가 학습 중이면 거절 · 다 마침이면 받는다 · 가장 앞선 짜기 전 코스가 아니면 거절 · 이미 검토 중인 코스는 거절.
    - 첫 코스 만들기가 실패해 버린 뒤 다시 받는다(로드맵 진행 중) — 06 §6.
    - 같은 코스에 받기 두 번이 동시에 와도 작업 하나 · 크레딧 하나 · 같은 작업 ID.
    - 남의 코스 · 단일 코스 · 없는 코스.
- 만들기 · 저장 — 운영 처리기 + LLM 스텁으로 워커 한 바퀴:
    - 재료 — 첫 코스는 수준이 있고 앞 목록이 없다 · 세 번째 코스는 수준이 없고 두 번째 코스의 실제 목록만 · 뒤 코스 계획만 들어간다(스텁이 받은 요청 또는 재료 값으로 확인).
    - 성공 — 강의 · 코스 검토 중 · 제목은 계획의 것 · 작업 성공 결과가 그 코스.
    - 실패 — 코스는 짜기 전으로 남고 강의가 없다 · 크레딧 복구.
- 단위 — 받기 규칙의 갈래(Fake).

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 아키텍처 체크리스트를 확인한다:
   - 받기 처리기와 생성 처리기를 짝으로 더했는가?
   - 첫 코스의 받기가 같은 트랜잭션에서 로드맵을 진행 중으로 바꾸고, 거절되면 아무것도 바뀌지 않는가?
   - 끝나지 않은 로드맵 다시 짜기가 있으면 거절하는가(ADR-182)? 다음 코스가 앞 코스 다 마침을 요구하는가?
   - 재료가 바로 앞 코스 하나 · 뒤 코스들의 계획 · 수준은 첫 코스만인가?
   - 재료를 읽는 트랜잭션이 LLM 호출 전에 닫히는가? `generation` 에 `@Transactional` 이 없는가?
   - `AGENTS.md` 금지 목록 · 작업 방식(TDD)을 위반하지 않았는가?
3. 결과에 따라 `phases/7-course-planning/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`. 담을 것: 처리기 클래스 · 새 오류 code 와 문구 · 상태를 바꾸는 엔티티 메서드 · 재료를 읽는 방법(step 5 가 다시 짜기에서 쓴다) · 서버 테스트 수(전후)
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 (계약 문서와 코드가 맞지 않음 등) → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- 다시 짜기(`REPLAN_*`)의 처리기를 만들지 마라. 이유: step 5 의 범위다.
- 다음 코스를 저절로 만들지 마라 · 앞 코스의 복습을 조건으로 넣지 마라. 이유: ADR-018 — 사용자가 누르고, 조건은 학습 완료뿐이다.
- 로드맵 · 코스 읽기 API · 코스 「이대로 시작」 · 제목 고치기를 만들지 마라. 이유: step 6 의 범위다.
- 관련 개념 검색 · 숙련도를 넣지 마라. 이유: 숙련도 고리 TASK 의 일이다.
- 실제 OpenAI 를 부르지 마라. 이유: 비용.
- 작업에 적지 않은 운영 로그 줄(`INFO` 이상)을 더하지 마라. 이유: 줄마다 14일 · 500MiB 보관을 나눠 쓰고, DB 에 남는 사실은 DB 에서 본다.
- 계약 문서(규칙 문장 · ADR · `AGENTS.md` 금지 목록 · README)의 규칙을 고치지 마라. 이유: phase 전에 정해 커밋했다. 어긋나면 `blocked`.
- 커밋하지 마라. 이유: Claude 리뷰가 승인한 뒤 하네스가 커밋한다.
- 기존 테스트를 깨뜨리지 마라
