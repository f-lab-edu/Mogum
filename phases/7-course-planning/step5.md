## 배경

검토 중인 코스 · 로드맵 계획을 피드백으로 다시 짜는 `REPLAN_COURSE` · `REPLAN_ROADMAP` 의 받기 처리기와 생성 처리기를 짝으로 더한다. 이것으로 이 TASK 의 다섯 종류가 모두 운영에서 받아진다(`MATERIAL` 은 강의 자료 TASK).

**계약 문서는 이 phase 전에 정해 커밋했다(`fa5af24`). 어긋나면 코드를 계약에 맞추고, 맞출 수 없으면 `blocked` 로 멈춰라. 계약 문장을 고치지 마라.**

## 작업

### 1. 받기

- **코스 다시 짜기** — 코스(단일 · 로드맵의 코스 모두)가 **검토 중**일 때만 받는다(ADR-007 — 시작한 뒤에는 다시 짜지 않는다).
- **로드맵 다시 짜기** — 로드맵이 **검토 중**일 때만 받는다(ADR-009). 검토 중인 로드맵의 코스는 모두 짜기 전이다(첫 코스 받기가 로드맵을 진행 중으로 바꾸므로 — step 4).
- 받지 않는 까닭의 오류 code 는 정해 `ErrorCode` · 05 §1.2 에 더한다 — 이미 있는 것과 사용자가 할 일이 같으면 그것을 쓴다(ADR-088).
- 같은 대상의 성공하지 않은 다시 짜기가 있으면 틀이 그 작업을 돌려준다(이미 있는 동작 — ADR-157).

### 2. 만들기 — 재료

- 재료는 `TransactionTemplate` 의 읽기 트랜잭션에서 값으로 읽고 닫은 뒤 LLM 을 부른다(금지 3 · 4). 예외를 던지지 마라.
- **코스 다시 짜기** — 지금 강의 목록 + 피드백 + 입력. 단일 코스는 코스의 입력, 로드맵의 코스는 step 4 와 같은 재료(로드맵의 입력 · 수준은 첫 코스만 · 이 코스의 계획 · 바로 앞 코스의 실제 목록 · 뒤 코스들의 계획). step 4 의 재료 읽기를 다시 쓴다. 코스 제목은 받지 않는다.
- **로드맵 다시 짜기** — 지금 계획(로드맵 제목 · 설명 · 코스마다 제목 · 한두 줄 설명 · 다룰 개념 — 사용자가 고친 코스 제목 그대로) + 피드백 + 로드맵의 입력.
- 피드백은 이 작업에만 있고(02 §2.4) 강의 자료로 넘기지 않는다.

### 3. 저장 — 성공할 때만 바꾼다

- **코스** — 이전 강의를 지우고 새 강의를 순서 1부터 넣는다. **코스 제목은 바꾸지 않는다**(ADR-183). 상태는 검토 중 그대로다.
- **로드맵** — 제목 · 설명을 새 것으로 바꾸고(ADR-167), 짜기 전 코스들을 지운 뒤 새 계획의 코스들을 순서 1부터 짜기 전으로 넣는다. 상태는 검토 중 그대로다.
- **지운 뒤 `flush()` 하고 넣는다** — `UNIQUE (course_id, position)` · `UNIQUE (roadmap_id, position)` 가 있고, Hibernate 는 INSERT 를 DELETE 보다 먼저 보낸다(금지 27). 부모 컬렉션 · cascade · orphanRemoval 로 바꾸지 마라.
- 저장 때 대상이 검토 중이 아니거나(코스 · 로드맵) 로드맵의 코스가 짜기 전이 아니면 불변식 위반이다 — 받기 규칙과 ADR-182(시작은 끝나지 않은 다시 짜기가 있으면 받지 않는다)가 막는다. 조용히 넘기지 마라.
- 지우는 강의 · 짜기 전 코스를 가리키는 다른 행(작업 · 강의 자료 · 카드)은 검토 중에는 생기지 않는다 — 강의는 학습 중에만 열고(강의 자료 · 카드), 로드맵의 코스 작업은 로드맵이 진행 중이 된 뒤에만 생긴다(step 4). 그래서 지울 때 그런 행을 따로 지우는 코드를 넣지 않는다.
- `ResultRef` 는 원래 대상 ID 다.

### 4. 테스트

- 받기 — `@IntegrationTest`: 검토 중이면 받는다 · 학습 중 코스 · 진행 중 로드맵은 거절(아무것도 안 바뀜) · 같은 대상 두 번이면 작업 하나 · 크레딧 하나 · 남의 것 `NOT_FOUND`.
- 만들기 · 저장 — 운영 처리기 + LLM 스텁으로 워커 한 바퀴:
    - 코스 — 성공하면 강의가 새 것으로 바뀌고 **제목은 사용자가 고친 그대로**다 · 피드백 · 이전 목록이 재료에 들어간다 · 로드맵의 코스면 step 4 의 재료도.
    - 로드맵 — 성공하면 제목 · 설명 · 짜기 전 코스들이 새 것으로 바뀐다(수가 늘거나 줄어도) · 이전 계획(고친 코스 제목 포함)과 피드백이 재료에 들어간다.
    - **실패하면 이전 것이 그대로다**(07 §1) — 강의 · 계획 · 제목 · 설명 모두 · 크레딧 복구. 실패를 버려도 그대로다.
- 단위 — 받기 갈래(Fake).

### 5. 문서 — 구현으로 정해진 사실만

- `docs/05-api.md` §1.2 — 새 오류 code(있다면). §2 — 받는 종류에 `REPLAN_COURSE` · `REPLAN_ROADMAP` 를 더한다.
- `docs/04-jobs-and-cost.md` §2.3 — 처리기 한 줄 · 교체할 때 flush 순서.

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 아키텍처 체크리스트를 확인한다:
   - 받기 처리기와 생성 처리기를 짝으로 더했는가? 검토 중에만 받는가?
   - 코스 다시 짜기가 제목을 바꾸지 않는가(ADR-183)? 로드맵 다시 짜기가 제목 · 설명 · 코스들을 모두 바꾸는가?
   - 지운 뒤 flush 하고 넣는가? 컬렉션 · cascade 를 쓰지 않았는가?
   - 실패하면 이전 것이 그대로인가?
   - `AGENTS.md` 금지 목록 · 작업 방식(TDD)을 위반하지 않았는가?
3. 결과에 따라 `phases/7-course-planning/index.json`의 해당 step을 업데이트한다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`. 담을 것: 처리기 클래스 · 오류 code · 교체 방법 · 서버 테스트 수(전후)
   - 수정 3회 시도 후에도 실패 → `"status": "error"`, `"error_message": "구체적 에러 내용"`
   - 사용자 개입 필요 (계약 문서와 코드가 맞지 않음 등) → `"status": "blocked"`, `"blocked_reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- 시작한 코스 · 진행 중인 로드맵을 다시 짜는 길을 만들지 마라. 이유: ADR-007 · ADR-009 — 01 §6 「하지 않는 것」.
- 코스 다시 짜기에서 코스 제목을 바꾸지 마라. 이유: ADR-183.
- 반영하지 못한 피드백을 알리는 칸 · 문구를 만들지 마라. 이유: ADR-045.
- 코스 · 로드맵 읽기 API · 「이대로 시작」 · 제목 고치기를 만들지 마라. 이유: step 6 의 범위다.
- 실제 OpenAI 를 부르지 마라. 이유: 비용.
- 작업에 적지 않은 운영 로그 줄(`INFO` 이상)을 더하지 마라. 이유: 줄마다 14일 · 500MiB 보관을 나눠 쓰고, DB 에 남는 사실은 DB 에서 본다.
- 계약 문서(규칙 문장 · ADR · `AGENTS.md` 금지 목록 · README)의 규칙을 고치지 마라. 이유: phase 전에 정해 커밋했다. 어긋나면 `blocked`.
- 커밋하지 마라. 이유: Claude 리뷰가 승인한 뒤 하네스가 커밋한다.
- 기존 테스트를 깨뜨리지 마라
