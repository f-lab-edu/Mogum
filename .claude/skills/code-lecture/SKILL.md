# code-lecture — 작업 단위 코드 설명 페이지

사용자는 이 저장소의 구현을 Codex 에 맡기고 자신은 기획 · 리뷰를 한다. 그래서 코드를 직접 쓰지 않은 채로 「왜 이렇게 짰는지」를 이해해야 한다. 이 스킬은 한 작업(브랜치 · PR · TASK)을 장과 단계로 나눈 설명 페이지로 만든다. 단계마다 도식에서 지금 다루는 부분이 강조되고, 오른쪽 코드 칸에 실제 파일의 해당 줄이 강조되고, 그 아래 자세한 설명이 붙는다. 사용자가 ← → 로 직접 넘기며 읽는다(음성 · 자동 재생 없음).

페이지는 이 저장소의 코드만 설명하지 않는다. 코드가 기대는 기술(DB 잠금 · 트랜잭션 · 프레임워크 동작 등)을 개발자로서 알아 둘 만큼 함께 가르치고(「더 알아두기」 상자 · 배경 지식 장), 끝에 퀴즈로 전체를 이해했는지 확인한다.

페이지 모양은 `assets/player.html` 에 고정되어 있다. 매번 하는 일은 **내용(`lecture.json`)을 쓰는 것**이고, `scripts/build.py` 가 코드를 실제 파일에서 잘라 넣고 내용을 검사한 뒤 페이지를 만든다. 형식은 `references/lecture-format.md`, 작은 완성 예는 `references/example.lecture.json` 이다 — 내용을 쓰기 전에 둘 다 읽는다.

답과 페이지는 모두 한국어다.

## 1. 대상 정하기

사용자가 대상을 준다. 셋 중 하나다. 주지 않았으면 무엇을 설명할지 한 번만 묻는다.

| 대상 | 범위를 읽는 법 | 발췌 기준 커밋(`source.rev`) |
|---|---|---|
| **지금 브랜치** — 요청한 그 브랜치에서 한 작업 | `git merge-base HEAD origin/main` 을 기준점으로 `git log --oneline <base>..HEAD` · `git diff --stat <base>` · `git diff <base>`. 커밋하지 않은 변경도 포함 | 커밋하지 않은 변경이 있으면 rev 를 비워 작업 트리를 읽고 foot 에 그렇게 적는다. 없으면 `HEAD` 의 짧은 SHA |
| **과거 PR** — 번호 | `gh pr view <N> --json title,body,headRefName,mergeCommit,headRefOid,commits,files` · `gh pr diff <N>` | 병합됐으면 `mergeCommit.oid`, 열린 PR 은 `headRefOid`(없으면 `git fetch origin pull/<N>/head`) |
| **과거 TASK** — `phases/` 의 이름(예: `6-job-worker`) | `phases/<task>/index.json` 의 step `summary` · `review_notes`, `phases/<task>/step*.md`, `gh pr list --state merged --head feat-<task> --json number,mergeCommit` 로 찾은 PR 의 diff | 그 PR 의 병합 커밋. 지금 코드가 아니라 **그 작업이 끝났을 때의 코드**를 보여 준다 — foot 에 커밋을 적는다 |

지금 브랜치가 `main` 이면 「지금 브랜치」는 설명할 작업이 없다 — 대상을 다시 묻는다.

## 2. 읽기 — 설명할 수 있을 만큼 이해하기

페이지의 가치는 정확함이다. 틀린 설명은 없는 설명보다 해롭다 — 사용자는 이 페이지를 믿고 리뷰한다.

1. **바뀐 파일 목록부터** — `--stat` 으로 무엇이 큰지 본다. 테스트 · 문서 · 생성 결과물(`phases/*-output.json`)은 흐름을 이해하는 재료로만 쓴다.
2. **설계 의도** — TASK 면 step 파일의 「배경」 · 「작업」 · 「금지사항」이 왜를 알려 준다. 관련 `docs/` 절, `AGENTS.md` 금지 목록, ADR 을 읽는다. 설명의 「왜」는 대개 여기서 온다.
3. **진입점에서 끝까지 따라가기** — 요청 · 스케줄 · 이벤트가 들어오는 곳에서 시작해 결과가 저장 · 응답될 때까지 호출을 따라 읽는다. diff 조각만 보지 말고 바뀐 파일은 통째로, 바뀌지 않았어도 흐름에 필요한 주변 코드(호출하는 쪽 · 표 정의 · 설정)도 읽는다.
4. **사실 확인** — 설명에 쓸 숫자(시한 · 횟수 · 크기) · 상태 이름 · 오류 code 는 그 rev 의 코드 · 설정에서 확인한 값만 쓴다. 확인하지 못한 것은 「확인하지 못했다」로 쓴다.
5. **눈에 띈 점 모으기** — 읽다가 빈틈 · 위험 · 문서와 다른 곳이 보이면 적어 둔다. 페이지의 정리 장과 최종 답에 「눈에 띈 점」으로 따로 낸다 — 확인한 결함인지 의심인지 구분해서.
6. **개발 지식 모으기** — 코드가 기대지만 코드에는 보이지 않는 동작을 적어 둔다(예: `FOR UPDATE SKIP LOCKED` 의 잠금 동작, 트랜잭션 격리 수준, JPA flush · 프록시, Spring 트랜잭션의 self-invocation, 쿠키 세션 · CSRF). 버전마다 다른 동작은 저장소가 쓰는 버전(`build.gradle` · `compose.yaml` · `package.json`)을 확인해 그 버전 기준으로 쓴다. 근거를 댈 수 없는 지식은 쓰지 않는다.

## 3. 장 설계

한 장 = 도식 하나 + 한 가지 주제. 한 단계 = 한 가지 생각.

**순서** — 사용자가 처음 보는 사람이라고 생각하고, 큰 그림에서 실행 순서로 내려간다.

1. **큰 그림** — 구성 요소와 흐름 전체. 코드 칸에는 이 작업이 만든 것을 `list:` 로 띄운다.
2. **상태 · 데이터 모양**(있으면) — 상태 기계 · 표. 뒤 장들이 이 이름을 쓴다.
3. **실행 순서대로 한 장씩** — 요청이 들어와서 끝날 때까지. 경계(트랜잭션 · 패키지 · 외부 호출)가 바뀌는 곳에서 장을 나눈다.
4. **지키는 규칙 장**(있으면) — 동시성 · 시한 · 재시도 · 지우기처럼 여러 곳에 걸친 불변식. 시간이 중요하면 실제 비율의 시간 막대를 그린다.
5. **정리** — 핵심 세 가지, 직접 읽을 때의 파일 순서(`list:`), 리뷰할 때 들고 갈 질문, 눈에 띈 점.
6. **퀴즈** — 정리 장 뒤에 페이지가 자동으로 붙인다(§6).

**배경 지식 장**(`kind: "background"`) — 여러 장에 걸쳐 쓰이거나 상자 하나로는 모자란 개념(예: Postgres 행 잠금, 펜싱 토큰, 트랜잭션 전파)은 따로 장을 만든다. 그 개념을 처음 쓰는 코드 장 **바로 앞**에 둔다. 한 단계에서만 쓰이는 개념은 장이 아니라 그 단계의 「더 알아두기」 상자로 넣는다(§5).

**분량** — 작은 PR 은 3~6장, TASK 하나는 8~14장(배경 장 포함, 배경 장은 그중 1~3장). 장마다 3~7단계. 같은 말을 두 장에서 하지 않는다.

## 4. 설명 쓰기

`say` 는 그 단계의 요점 한두 문장이다. 굵게 크게 보이므로 그것만 읽어도 흐름이 따라와야 한다.

`detail` 이 이 페이지의 핵심이다 — 사용자가 음성 대신 원한 「더 자세한 설명」이다. 두세 문단(필요하면 글머리 목록)으로, 문단마다 두세 문장. 아래 중 그 단계에 맞는 것을 쓴다.

- **무엇** — 강조한 줄이 하는 일을 코드 이름과 함께. 「155행의 `FOR UPDATE SKIP LOCKED` 는 …」처럼 코드 칸과 잇는다.
- **왜** — 이렇게 짠 이유. 근거가 규칙 · ADR · 문서면 `refs` 에 꼬리표로 단다(`AGENTS 금지 9` · `ADR-126` · `04 §4.1`).
- **안 하면 무엇이 깨지나** — 구체적인 장면 하나. 「워커 A 의 호출이 시한을 넘겼다고 해 봅시다 …」처럼 숫자 · 순서가 있는 이야기가 가장 잘 이해된다.
- **이어짐** — 앞 · 뒤 단계나 다른 장과의 관계.

쓰는 법:

- 사용자는 백엔드 개발자다. 언어 · 프레임워크 기초는 설명하지 않고, **이 코드가 내린 결정**을 설명한다.
- 화면은 번호(U11)가 아니라 이름 · 생김새로 부른다.
- 코드 이름 · 값은 `` `백틱` ``, 꼭 기억할 말만 `**굵게**`.
- 「중요합니다」 「핵심입니다」로 강조하지 말고 이유를 쓴다.
- 지어내지 않는다. 의심은 의심이라고 쓴다.

## 5. 더 알아두기 — 코드 밖의 개발 지식

`detail` 이 「이 코드가 내린 결정」이라면, `know` 상자는 그 결정이 기대는 **일반 지식**이다. 사용자가 이 코드를 넘어 다른 프로젝트 · 면접 · 장애 대응에서도 쓸 수 있는 것을 고른다.

넣을 만한 것:

- **아래층 동작** — 코드 한 줄 뒤에서 DB · 프레임워크 · 런타임이 실제로 하는 일(잠금을 언제 잡고 놓는지, 프록시가 어떻게 끼어드는지).
- **다른 길과 득실** — 업계에서 같은 문제를 푸는 다른 방법과, 이 저장소가 그것을 고르지 않은 이유(이유가 ADR · 문서에 있으면 꼬리표로).
- **흔한 함정** — 그 기술을 처음 쓰는 사람이 자주 틀리는 것.
- **더 읽을 곳** — 공식 문서의 장 이름 · 책 이름과 장. URL 은 지어내지 않는다.

쓰는 법:

- 필요한 단계에만 — 장마다 0~2개. 모든 단계에 붙이면 아무것도 눈에 띄지 않는다.
- `body` 는 두세 문단(또는 글머리 목록). 상자 하나에 개념 하나.
- 이 저장소 이야기는 `detail` 에, 일반 지식은 `know` 에 — 섞지 않는다. 단 「그래서 이 코드는 …」 한 문장으로 다시 잇는 것은 좋다.
- 정확함이 코드 설명과 같은 무게다. 버전 · 설정에 따라 다르면 그 조건을 적고, 확실하지 않으면 빼거나 「확인하지 못했다」로 쓴다.

## 6. 퀴즈 — 이해도 확인

사용자가 강의를 다 넘긴 뒤 전체를 이해했는지 스스로 확인하는 문항이다. 형식은 `references/lecture-format.md` 의 「quiz」.

**문항 수** — 작은 PR 은 4~6개, TASK 하나는 8~12개. 그중 **서술형 2~3개**, 나머지는 객관식.

**무엇을 묻나** — 장마다 한 문항 이상이 고르게 가도록, 아래를 섞는다.

- **흐름** — 요청이 들어와 끝날 때까지 무엇이 어떤 순서로 일어나나.
- **왜** — 이 코드가 내린 결정의 이유(ADR · 금지 목록에 근거가 있는 것).
- **깨지는 장면** — 「이 줄을 빼면 / 순서를 바꾸면 무엇이 깨지나」. 서술형에 가장 잘 맞는다.
- **개발 지식** — 「더 알아두기」 · 배경 장에서 다룬 일반 지식. 전체의 1/4 쯤.

외워서 맞히는 문항(줄 번호 · 클래스 이름 맞히기)은 내지 않는다 — 이해했으면 맞히고 이해하지 못했으면 틀리는 문항을 낸다.

**객관식 쓰는 법**

- 보기 4개가 기본. 오답은 **그럴듯한 오해**로 만든다 — 대충 읽은 사람이 고를 만한 것. 말이 안 되는 보기는 문항을 쉽게만 만든다.
- 정답 위치를 섞는다. 「모두 맞다 · 모두 틀리다」 보기는 쓰지 않는다.
- `why` 는 정답의 이유와, 가장 헷갈리는 오답이 왜 틀렸는지를 함께 쓴다.

**서술형 쓰는 법**

- 한두 문단으로 답할 수 있는 질문 — 「왜」 「빼면 무엇이 깨지나」 「다른 방법으로 바꾸면 무엇이 달라지나」.
- `model` 은 사용자가 쓸 법한 길이로. `points` 에 맞은 답이면 꼭 들어 있을 것 2~4개를 적는다 — 사용자는 이것으로 스스로 채점한다.

**공통** — 모든 문항에 `see`(다시 볼 단계)를 단다. 문항의 답은 강의 안에 있어야 한다 — 강의에서 다루지 않은 것을 묻지 않는다. 답과 해설도 §2 의 사실 확인을 거친 것만 쓴다.

## 7. 도식

`references/lecture-format.md` 의 nodes · edges 를 따른다. 요령:

- 상자 이름은 한국어 뜻(`l`), 작은 글씨는 코드 이름 · 표 이름(`s`). 사용자가 코드에서 그 이름을 찾을 수 있게.
- 흐름은 한 방향으로. 한 장에 상자 9개 이하. 트랜잭션 · 경계는 `box` 로 감싼다.
- 단계의 `on` · `e` 로 지금 말하는 것만 강조한다 — 강조가 없는 단계(전체를 다시 볼 때)도 괜찮다.

## 8. 조립 · 확인

작업 폴더는 세션 scratchpad 안 `lectures/<짧은-이름>/` 이다(없으면 만든다). 저장소 안에 내용 파일 · 페이지를 두지 않는다.

```bash
python3 -I .claude/skills/code-lecture/scripts/build.py <작업폴더>/lecture.json <작업폴더>/lecture.html --repo <저장소 루트>
```

- **오류**가 나면 페이지가 만들어지지 않는다 — 메시지대로 고치고 다시 돌린다. `hl` 이 줄에 없다는 오류는 대개 발췌 범위가 틀렸거나 줄의 실제 글자가 다른 것이다 — 파일을 다시 보고 고친다.
- **경고**(상자 겹침 · 안 쓰는 발췌 · 긴 발췌 · 퀴즈 종류 · 정답 위치)도 읽고 고칠지 판단한다.
- 화면 확인 — Playwright 로 넓은 폭(1360)과 폰 폭(390)을 한 번씩 본다. 도식 글자가 상자를 넘치는지, 강조가 맞는 줄에 가는지, 가로 스크롤이 생기는지, 퀴즈 화면의 문항 · 보기가 넘치지 않는지 본다.
  - `file://` 은 막혀 있다. 작업 폴더에서 `python3 -I -m http.server <포트> --bind 127.0.0.1` 로 띄운다(백그라운드).
  - 원본에는 문서 머리가 없어 한글이 깨져 보인다. 미리보기용 사본을 만든다: `{ printf '<!doctype html><meta charset="utf-8"><meta name="viewport" content="width=device-width, initial-scale=1">\n'; cat lecture.html; } > preview.html` — 올리는 것은 원본이다.
  - 다 보면 서버를 끄고(`pkill -f "http.server <포트>"`), Playwright 가 현재 디렉터리에 만든 `.playwright-mcp/` 의 파일을 **이름을 하나씩 적어** 지운 뒤 `rmdir` 한다. `rm -rf` 와 glob 삭제는 훅 · 안전 검사가 막는다.

## 9. 올리기 · 알리기

`Artifact` 도구로 `<작업폴더>/lecture.html` 을 올린다 — 첫 게시에는 `icon: "book"` 과 한 문장 `description`. 비공개로 올라가며 사용자가 공유를 정한다. `player.html` 이 아티팩트 페이지 규칙(제목 · 색 토큰 · 다크 모드 · 폰 폭 · 외부 스크립트 없음)을 이미 지키므로 틀을 고치지 않는 한 내용만 신경 쓴다.

답에는:

- 링크와 장 · 단계 수, 퀴즈 문항 수, 읽는 데 걸리는 시간(조립 결과 줄의 어림값).
- 장 순서 한 줄(배경 장은 표시).
- 코드 기준 커밋.
- **눈에 띈 점** — 확인한 것과 의심을 나눠서, 파일 · 줄과 함께.

퀴즈의 답은 답에 싣지 않는다 — 사용자가 페이지에서 직접 푼다.

고칠 때는 같은 `lecture.html` 경로로 다시 올리면 같은 링크가 갱신된다. 다른 세션에서 고칠 때는 아티팩트를 읽으면 페이지 안의 `const L = {...}` 에 내용 전체가 들어 있다 — 그것을 `lecture.json` 으로 되살려 고친다(발췌는 이미 잘린 줄이므로 `snippets` 는 원래 `file` · `from` · `to` 로 다시 적는다).

페이지 틀(`assets/player.html`)이나 `scripts/build.py` 를 고치면 `python3 -m pytest .claude/skills/code-lecture/scripts/test_build.py` 를 돌리고, `references/example.lecture.json` 을 조립해 화면으로 본다.

## 하지 않는 것

- 제품 코드(`backend/` · `frontend/`) · 문서를 고치지 않는다. 이 스킬은 읽고 설명만 한다. 고칠 것이 보이면 「눈에 띈 점」으로 알린다.
- `docs/PORTFOLIO.md` 에 기록하지 않는다 — 포트폴리오 기록은 사용자 확인 뒤에만 한다.
- `.env` · 키를 읽거나 페이지에 싣지 않는다. 설정 값은 `application.yml` 처럼 저장소에 있는 것만 쓴다.
