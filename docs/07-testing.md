# 07. 테스트 · 용량 측정 · LLM 스텁

> 무엇으로 *"깨지지 않는다"* 를 보이나. 장애 주입은 **코드로 남는 증거**이고, 용량 측정은 **정원을 정하는 숫자**다.
> 부하 테스트는 고장을 재현하려고 하지 않는다 — **이 서버 한 대로 몇 명까지 받을지**를 재려고 한다.

---

## 1. 반드시 있어야 하는 테스트

### 1.0 로컬 서버 테스트 실행

- Docker를 실행한 뒤 `./gradlew test`로 전체 서버 테스트를 실행한다. DB 테스트는 Testcontainers가 별도 PostgreSQL을 띄우며, 실제 Google 인증 대신 가짜 설정과 HTTP 서버를 사용한다.
- Gradle `test` 작업은 테스트용 `GOOGLE_CLIENT_ID` · `GOOGLE_CLIENT_SECRET` 시스템 속성을 주입한다. VS Code의 Test Runner for Java에서 직접 실행할 때는 Gradle 작업을 거치지 않으므로, 로컬 `.vscode/settings.json`에 같은 값을 지정한다. `.vscode/`는 Git 추적 대상이 아니다. 아래 항목을 기존 설정에 추가한다([VS Code 공식 문서](https://code.visualstudio.com/docs/java/java-testing#_customize-test-configurations)).

```json
{
  "java.test.config": {
    "name": "mogum",
    "vmArgs": [
      "-DGOOGLE_CLIENT_ID=test-google-client",
      "-DGOOGLE_CLIENT_SECRET=test-only-not-a-real-secret"
    ]
  },
  "java.test.defaultConfig": "mogum"
}
```

`ApplicationContext failure threshold (1) exceeded`는 같은 Spring 컨텍스트의 초기화가 앞서 실패했다는 후속 오류다. 이 문구만으로 원인을 판단하지 않고, 최초 `Failed to load ApplicationContext`의 `Caused by`를 확인한다. 위 테스트 설정이 없으면 `Client id of registration 'google' must not be empty`로 초기화가 실패할 수 있다.

### 1.1 장애 주입 — 실제 PostgreSQL(Testcontainers) 위에서

| # | 상황 | 기대 | 확인하는 메트릭 |
|---|---|---|---|
| 1 | 같은 강의를 **동시에 두 번** 요청 | 잡 하나 · 두 번째 응답도 같은 `jobId` | 기존 잡 연결 수 |
| 2 | 실행기 둘이 **동시에 수령** | 같은 잡을 두 번 가져가지 않는다 | — |
| 3 | 리스를 강제로 만료시킨 뒤 **옛 실행기가 저장** | `0 rows` 로 거부 · 옛 실행기 즉시 중단 | `job.write.fenced` · `job.lease.lost` |
| 4 | 실행 중 **`kill -9`** | 리스 만료 뒤 회수 · **끝낸 단계 다음부터** 재개 | `job.reclaimed` |
| 5 | 실행 중 **SIGTERM**(배포) — 본문 호출 중 · ① 중간 라운드 중 · 백오프 대기 중 · 유예(120초)를 넘기는 느린 호출(스텁) | 새 수령 0건. 본문 호출은 끝까지 받아 단계 산출물을 저장한 뒤 반납 → 다음 기동에서 **카드 단계부터** 이어받음(본문 재호출 0회). ① 중간 라운드는 사용량만 기록하고 반납. 백오프 중이면 기다리지 않고 반납. 유예를 넘기면 즉시 반납하고 늦은 응답은 원장에만 기록. 모두 원래 순서 자리 | `job.released` · 단계별 호출 수 · 원장 대조 |
| 6 | 본문이 **토큰 상한에서 잘림**(스텁) | 이어 쓰기 최대 1회 · 같은 생성 시도 안에서 처음부터 자동 재요청 0회. 이어 쓰기 뒤에도 잘리면 `LLM_OUTPUT_INVALID`, 카드 생성/자료 저장 없음 | `body.truncated` · `body.continued` · `body.continuation.failed` |
| 7 | **카드 단계 실패**(스텁) | 재시도는 카드 단계만 · 개요 · 본문 호출 **추가 0회** | 단계별 호출 수 |
| 8 | **리스 상실 후 사용량 응답** — 외부 호출 중 다른 실행기가 회수 | 옛 실행기의 확인된 사용량은 원장 행에 1회 확정되어 합계 쿼리에 잡힌다. 잡 · 산출물 변경과 다음 외부 호출은 없음 | `job.lease.lost` · 원장 대조 |
| 9 | **사용량 확정 실패** — 원장 행 갱신 중 DB 오류 | 그 행만 롤백되고 합계 쿼리는 확정 전 값 그대로. 같은 시도 ID로 기록 재시도하면 한 번만 확정 | 원장 상태 · 합계 쿼리 |
| 10 | **사용량 커밋 응답 유실 · 중복 기록** | 같은 시도 ID의 동시 기록 · DB 재시도에서 두 번째부터는 `0 rows`(이미 `KNOWN`) — 합계에 한 번만 잡힌다. 외부 재호출 0회 | 스텁 수신 건수 · 원장 대조 |
| 11 | **호출 등록 후 또는 응답 수신 직후 `kill -9`** | 기록 못 한 시도는 `PENDING` 으로 남고 시한 뒤 미확인에 포함. 전송 여부 · 과금액을 0이나 확정값으로 꾸미지 않는다 | DB 미확인 건수 |
| 12 | **원장 DB 쓰기 장애** — 호출 전 등록 / 호출 후 결과 기록 실패 | 등록 커밋 확인 전 외부 호출 0회. 결과 기록 실패 시 DB만 최대 3회 재시도하고 다음 외부 호출 중단. 실패 상태 저장 불가 시 기존 리스 회수 경로 | 스텁 수신 건수 · `USAGE_RECORD_FAILED` |
| 13 | **호출 상한 마지막 1회 경합** — 현재 실행기 · 만료된 실행기 및 등록 DB 재시도 | 실행 권한 있는 새 시도 한 행만 추가. 같은 ID의 재확인은 추가 차감 0회, 한도 초과 전송 0회 | 원장 종류별 건수 · 스텁 수신 건수 |
| 14 | **누적 상한 유지** — 반복 `kill -9` · SIGTERM · API 재시도 · 한국 자정 통과 | 미확인 · 전송 전 종료도 누적 몫을 사용. 원장과 적재 시 상한 유지, 추가 호출 필요 시 `JOB_CALL_LIMIT_EXCEEDED`. 재시도 API · 강의 다시 열기로 새 잡을 만들지 않는다 | 원장과 스텁 대조 · 실패 코드 |
| 15 | **마지막 허용 호출 성공 · 상한 소진 뒤 늦은 사용량** | 추가 외부 호출 없이 완성 가능한 작업은 성공. 상한 소진 뒤 돌아온 기존 시도의 사용량도 한 번만 확정 | 상태 · 원장 대조 |
| 16 | **장애 중 소진 → 장애 후 처음부터 다시 만들기** — 스텁 5xx 를 켜고 강의를 반복해 다시 연 뒤 끄고 `restart` | 다시 열기의 자동 재시도로 몫이 바닥나 `JOB_CALL_LIMIT_EXCEEDED`. 다시 열기는 새 잡을 만들지 않는다. `restart` 는 새 잡(새 몫 · 1단계부터)으로 성공하고 옛 잡과 원장은 남는다 | 잡 행 수 · 원장 `job_id` 별 건수 |

### 1.2 규칙 테스트

그룹 화면은 [06 §9](./06-screens.md)(U11)에서 정했다. 아래 분할 관련 검증은 기능 계약이 대상이며, 화면 테스트는 화면 TASK 에서 06 을 기준으로 쓴다. LLM의 단일/그룹 판단 적절성은 기존 콘텐츠 수동 채점에서 목표/범위/선행 관계를 확인하며 구조 테스트만으로 검증됐다고 쓰지 않는다.

회원/외부 로그인 식별자 분리(ADR-064)는 [02 §6.1](./02-domain-data.md)에 따라 구현했다. `LoginTest` · `LoginIT` · `JpaUserIdentityRepositoryIT` · `GoogleAccountMapperTest` · `OAuthLoginHandlerIT` · `UserIdentityMigrationIT`로 아래 계정 항목을 검증했다. 2026-10-19 전체 서버 테스트 196개가 통과했다. 작업/생성 등 아직 구현하지 않은 영역의 아래 항목은 해당 TASK의 검증 기준이다.

| 테스트 | 왜 |
|---|---|
| **ArchUnit**([04 §2](./04-jobs-and-cost.md)) — 첫 커밋 | 컨트롤러가 생성을 직접 부르면 1분짜리 요청이 조용히 되살아난다. `core` 에 `jakarta.persistence` 가 들어오면(엔티티가 `core` 로 새면) 빌드가 깨진다 |
| **외부 식별자 조회** — 같은 `(provider, subject)` · 다른 제공자의 같은 subject · 같은 이메일의 다른 식별자 | 같은 외부 계정은 같은 회원으로 찾고, 제공자나 식별자가 다르면 이메일이 같아도 기존 회원으로 자동 연결하지 않는다. 구글 외 제공자 값은 저장 모델의 구분 테스트에만 쓰며 실제 OAuth 제공자를 활성화하지 않는다 |
| **인증 입력의 출처** — 미등록 제공자 · 원본 응답의 식별자 누락 · 이메일 검증 누락 · 연결 조회 뒤 회원 삭제 | 제공자 값은 검증된 서버 등록에서만 결정하고 잘못된 인증 입력을 거절한다. 이미 찾은 연결의 회원이 사라졌다면 실패하며 회원/연결을 복원하지 않는다 |
| **회원/로그인 연결 원자성** — 연결 저장 실패 · 같은 식별자의 동시 첫 로그인 | 회원과 연결이 함께 커밋/롤백된다. unique 충돌로 실패한 요청이 연결 없는 회원을 남기지 않는다 |
| **재로그인 계정 보존** — 외부 이메일 변경 · 관리자 목록/저장 역할 불일치 | 기존 사용자 ID · 이메일 · 역할 · 상태 · 약관 · 가입 시각과 연결 행을 모두 보존하고, 세션 번호만 기존 정책으로 변경한다 |
| **계정 모델 이전** — V1~V3의 기존 회원/ID 세션에서 새 스키마로 이전 | 기존 사용자 ID와 전체 회원 정보가 유지되고, google_sub마다 `google` 연결 하나가 생긴다. 기존 세션으로 `/api/me`가 되고 동일 구글 계정 재로그인이 회원을 추가하지 않는다. 새 DB의 전체 마이그레이션 · JPA 검증도 함께 확인한다 |
| **JPA · 네이티브 혼합** — 같은 트랜잭션에서 엔티티를 바꾼 뒤 네이티브 쿼리로 읽기 | `flush()` 뒤에는 바뀐 값을 읽는다. 리포지토리 포트가 돌려준 record 에서 연관 데이터를 읽어도 `LazyInitializationException` 이 나지 않는다(완전히 채워져 있다) |
| **초기 통합 생성** — 단일/그룹 응답을 주는 스텁 | 정상 경로에 생성용 채팅 호출 1회. 단일은 목록 저장 후 잡 A 재호출 없음, 그룹은 분할안 저장 후 추가 분할안 호출/단계 상세 자동 생성 없음. 사용자 클릭 이후 상세 생성과 구분하고 검색 임베딩/오류 재시도는 원장에 별도 시도로 남김. 초기 잡/API/출력 계약 확정 후 검증하며 아직 실행 결과가 아님 |
| **초기 요청 중복 처리** — 연타/응답 유실 재전송 · 명시적 새 생성 | 같은 사용자/요청 ID/내용은 같은 작업 반환, 추가 생성 없음. 새 ID는 같은 주제라도 새 요청. 내용 충돌/동시 접수/삭제 후 재전송은 해당 TASK에서 구체화하고 검증. 삭제된 결과 복원 금지 원칙 유지. 아직 실행 결과가 아님 |
| **초기 입력 선저장 · 성공 시 생성** — 접수/대기/거절/실패 · 단일/그룹 성공 · 단계 생성 | 초기에는 잡 입력만 존재하고 결과 FK 모두 NULL. 단일 성공은 강의가 있는 DRAFT 하나, 그룹 성공은 전체 묶음/단계만 생성하며 상태/연결 FK/이벤트를 함께 커밋. 단계 생성은 기존 초안+잡 A 유지 |
| **초기 완료 원자성/멱등성** — 첫 조건부 UPDATE 0행 · 결과 일부 삽입/최종 연결/이벤트 실패 · 커밋 응답 유실 · 두 실행기 | 0행이면 도메인 쓰기 없음. 중간 오류는 새 결과/연결/성공/이벤트 전체 롤백. 같은 잡 성공 뒤 재저장은 새 결과를 만들지 않고 원래 FK를 반환. 검증된 응답 체크포인트가 있으면 저장 재개에 LLM 추가 전송 없음 |
| **초기 잡 FK/종류/예산** — 결과 없는 성공 · 실패에 결과 FK · 두 결과 FK · 옛 G 종류 · 재시도 | 잘못된 조합은 DB CHECK로 거절. I/A/B 종류는 불변이며 I의 성공 결과가 단일이어도 A 예산으로 바꾸지 않음. 실패 재시도는 request/선별/검증된 응답/누적 몫 유지. 최초 접수 중복 방지는 요청 식별자 방식으로 확정했고 구체적인 저장/경합 처리는 해당 TASK에서 설계 |
| **초기 복귀/소유권/삭제/탈퇴** — 새로고침 · 다른 기기 · 남의 잡 · 결과 단일 삭제 · 생성/탈퇴 경합 | 미완료 요청 조회는 본인 I의 대기/실행/실패만, 성공은 결과 종류/ID로 복귀. 성공 전 커리큘럼 조회/승인/삭제 대상 없음. 단일 결과 삭제는 연결 I/A/B를 함께 지움. 탈퇴는 미완료 I의 입력까지 지우고 먼저 커밋되면 늦은 결과 0행, 완료가 먼저면 결과까지 삭제. 외부 사용량은 독립 원장에 유지 |
| **작업 이벤트 원자성** — 성공/실패의 이벤트 삽입 실패 · 성공 산출물 저장 실패 · 회수 이벤트 삽입 실패 | 실제 PostgreSQL에서 상태 전환/이벤트/성공 산출물 전체 롤백. 회수 이벤트 실패면 수령 회차/리스/소유자 변경도 롤백. 이벤트만 남거나 상태만 바뀌지 않음 |
| **작업 이벤트 중복/펜싱** — 커밋 응답 유실 · 같은 전환 동시 재요청 · 옛 실행기의 실패/완료 요청 | 수령 회차당 종결 이벤트 최대 1개. 이미 반영한 전환의 재요청과 실행 권한 조건 `0 rows`는 추가 이벤트/도메인 쓰기 0회. 같은 잡/회차의 실패와 성공을 모두 삽입하려 하면 DB 제약으로 거절 |
| **회수 구분** — 최초 수령 · 정상 반납 후 수령 · 실패 후 재시도 · 리스 만료 `RUNNING` 수령 | 만료된 `RUNNING`의 새 수령만 `RECLAIMED` 1행. `lease_epoch > 1`인 다른 수령은 회수 아님. 수령 CTE는 갱신 결과를 반환하고 이전 상태로 회수 여부를 결정 |
| **실패율 이력/분모** — 실패 후 새 회차 성공 · 회수 후 성공 · 정식 주제 거절 · 빈 창 | 창 안 실패 1/성공 1이면 비율 0.5. 회수는 실패율 분모에 넣지 않음. 모든 정식 `FAILED` 포함/고정 실패 코드로 구분. 성공+실패 0이면 NULL이며 화면은 표본 없음 |
| **시간창/호출 지표 구분** — 창 시작/끝 경계 · 한국 자정 · 오래된 실패 잡의 오늘 재시도 · HTTP 코드 없음/429 · 전송 여부 미확인 재시도 등록 | 공통 DB `asOf`로 `[asOf-24h, asOf)` 적용. 과거 실패는 발생 시각으로 제외하고 새 성공만 포함. 429는 종료/HTTP 코드 확인된 호출, 호출 재시도 등록은 등록 시각/`is_retry`로 센다. 현재 상태나 잡 재실행 횟수로 대체하지 않음 |
| **삭제/탈퇴와 운영 이력** — 이벤트가 있는 커리큘럼 삭제/탈퇴 · 전환과 삭제 경합 · 삭제 뒤 늦은 쓰기 | 관련 잡 연결만 NULL, 이벤트 종류/시각/건수 그대로. 사용자/콘텐츠 원문 필드 없음. 전환 먼저면 연결 해제 후 이력 유지, 삭제 먼저면 새 이벤트 0행. 일반 사용자 API에서 운영 이력 조회 불가 |
| **`R` 일치** — 같은 `(S, 정수 경과일)` 에서 FSRS 라이브러리 `R` = SQL `R` | 공식이 두 곳에 있다. 라이브러리를 올리면 여기서 깨진다. 라이브러리는 경과일을 정수로 자르고 SQL 은 실제 경과 시간(소수 일)을 쓰므로 정수 경과일에서만 비교한다 — 공식 · 상수가 같은지를 본다([02 §8.3](./02-domain-data.md)) |
| **숙련도 생략 조건** — 같은 개념의 카드 복습 횟수 `3회 · 0회`, `3회 · 1회`, `2회 · 2회` | `loadUserMastery` · `lookupMastery` 모두 최소 횟수 `0` · `1` · `2`. 평균 `R ≥ 0.9` · `S ≥ 7일`이어도 앞의 두 경우는 `BRIEF` · `COMPRESSED`, 마지막만 `SKIP` · `EXCLUDED`. 마지막도 `R` 또는 `S` 조건을 못 채우면 생략하지 않는다 |
| **숙련도 집계 범위** — 전부 미복습 · 카드 없음 · 생성만 한 카드 · 새로 학습 완료한 카드 | 전부 미복습은 결과 행이 있고 `R/S=NULL` · 최소 횟수 `0`, 카드 없음과 구분한다. 생성만 한 카드는 집계에서 제외하며, 학습 완료하면 포함되어 기존 개념의 생략 조건을 해제한다. 미복습 카드는 `R/S` 평균에 섞지 않는다 |
| **숙련도 판정 경계** — `R=0.9/0.6` · `S=7/1일` · 최소 횟수 `2`의 경계와 각각 바로 아래 값, NULL | LLM 없이 `MasteryPolicy` 단위 테스트. 생략 조건을 먼저 적용하고 잡 A · B 판정이 같은 규칙에서 나온다. 표시용 반올림으로 임계값을 넘기지 않는다 |
| **커리큘럼 판정 위반** — 스텁이 허용되지 않은 `EXCLUDED` 또는 주입하지 않은 개념 ID 반환 | 저장하지 않고 기존 단계당 재요청 1회 안에서 수정 요청. 계속 위반하면 `LLM_OUTPUT_INVALID`, 이전 커리큘럼 유지. 성공 시 저장 근거는 모델이 쓴 수치가 아닌 백엔드 조회값 |
| **개요 판정 위반 · 참조 누락** — 스텁이 `DETAIL` 대상에 `SKIP` 출력, 미조회 ID · 빈 참조 · 여러 개념 참조 | ②가 받는 개요는 백엔드 판정 · 목표 분량으로 채워진다. 확인 불가 참조는 `DETAIL`, 여러 개념은 가장 상세한 판정. 모델의 임의 수치 · 판정은 저장 근거에 들어가지 않는다 |
| **생성 중 숙련도 변경 · 단계 재개** — 조회 후 복습, ③ 실패 후 재개 | 한 ① 실행의 같은 개념은 최초 조회값으로 판정 · 검증. 저장된 개요 · 근거를 ② · ③에서 재사용하고 최신 수치로 과거 판정을 덮어쓰지 않는다 |
| **복습 응답 유실** — 저장 성공 후 응답을 버리고 같은 요청 ID · 내용으로 재전송 | 최초 성공 응답 반환 · 복습 기록 1행 · FSRS 갱신과 버전 증가 각 1회. 이후 다른 복습이 있어도 이전 요청은 재반영하지 않는다 |
| **잘린 본문 이어 쓰기 성공** — 최초 `MAX_TOKENS`, 이어 쓰기 정상 종료 | 합친 본문의 6섹션/내용 검증 후에만 ② 완료와 ③ 호출. 첫 응답/이어 쓰기 사용량 모두 원장에 남고 완성 자료만 저장 |
| **이어 쓰기 후에도 잘림** — 두 응답 모두 `MAX_TOKENS`, 제목은 모두 존재 | 제목 유무와 무관하게 `FAILED(LLM_OUTPUT_INVALID)`. ③/임베딩 호출 0회 · 자료/카드 저장 없음 · 강의 `NOT_STARTED` 유지. 개요는 보존, 잘린 본문은 완료 체크포인트 아님. 두 응답 비용은 유지 |
| **본문 수정 몫 공유** — 이어 쓰기 후 섹션 누락/빈 내용 · 섹션 수정 뒤 상한 도달 | 이어 쓰기/섹션 수정 합쳐 1회만 허용. 몫 소진 뒤 추가 수정/이어 쓰기 없이 실패, 정상 종료만으로 잘못된 섹션을 저장하지 않음 |
| **본문 실패 후 명시적 재시도 · ③ 실패 후 재개** | 본문 실패는 ②부터 새 생성, 개요/숙련도 조회 재실행 없음 · 이전 호출 이력/상한 유지. 검증된 본문이 있고 ③에서 실패하면 ③만 재개. 불완전 본문이 U4 열람/학습 완료로 이어지지 않음 |
| **학습 완료 응답 유실 · 연속 재요청** | 최초/재요청 모두 `200`. 강의 완료와 카드별 상태 삽입 각 1회, 최초 시각/버전 유지. 완료 요청 자체가 복습 이력을 만들지 않음 |
| **학습 완료 동시 두 요청** — 실제 PostgreSQL에서 같은 강의 완료 동시 실행 | 같은 커리큘럼 잠금으로 직렬화. 두 요청 모두 성공, 카드별 상태 1행, 중복 삽입/초기화 없음 |
| **복습 후 학습 완료 재요청** — 일부/전부 첫 평가 후 완료 재전송 | FSRS 상태 · 난이도/안정성 · 날짜 · 복습 횟수/버전 · 이력 그대로. `reviewCards` 에는 현재 미평가 카드와 현재 버전만 반환, 모두 평가했으면 빈 배열. U4에 빈 첫 복습 버튼 없음 |
| **마지막 강의들의 동시 완료 · 전체 완료 후 재요청** | 서로 다른 마지막 강의의 완료를 직렬화해 커리큘럼도 `COMPLETED`. 전체 완료 후 같은 강의 재요청도 `200`, 완료 상태를 되돌리지 않음 |
| **학습 완료 저장 실패** — 카드 상태 일부 삽입 후 또는 커리큘럼 완료 전환 후 오류 | 강의 상태 · 카드 상태 삽입 · 커리큘럼 상태 모두 롤백. 재요청 시 정상적으로 최초 완료하며 기존 상태를 덮어쓰지 않음 |
| **학습 완료 상태/소유권 검사** — 자료 없는 강의 · 초안 · 남의 강의 · 삭제 후 재요청 | 최초 완료는 준비된 `ACTIVE` 강의에서만 가능. 자료 없음 `409 LESSON_NOT_READY`, 초안 `409 CURRICULUM_NOT_ACTIVE`, 남의 것/삭제 후는 `404`. 카드/복습 이력 생성 없음 |
| **복습 동시 재전송** — 같은 ID · 내용의 요청 둘을 동시에 제출 | 두 응답은 같은 성공 결과 · 기록과 상태 갱신은 한 번 |
| **복습 두 탭** — 다른 요청 ID · 같은 카드 버전으로 동시에 평가 | 하나만 성공 · 다른 하나는 `409 REVIEW_ALREADY_PROCESSED`. 충돌한 평가는 기록 · 횟수 · FSRS에 반영하지 않는다 |
| **복습 요청 ID 충돌** — 성공한 ID에 카드 · 등급 · 요청 버전 중 하나를 바꿔 제출 | `409 REVIEW_REQUEST_CONFLICT` · 상태 변화 없음 |
| **복습 저장 롤백** — 카드 상태 갱신 후 복습 기록 저장 실패 | 상태 · 버전 · 이력 모두 롤백. 같은 요청 재시도는 정상적으로 한 번 반영 |
| **복습 화면 재시도** — 응답 유실 · 다른 탭의 선행 평가 | 재전송 시 ID · 내용 유지, 성공은 요약에 한 번만 반영. 오래된 평가는 안내 후 건너뛰고 요약에 더하지 않으며 최신 버전으로 자동 재제출하지 않는다 |
| **탈퇴** — 스키마의 사용자 소유 테이블을 기준으로 학습 데이터 삭제 · 원장 연결 해제 확인 | 새 테이블을 탈퇴 처리 목록에 빠뜨리지 않는다. 그 사용자의 `concepts` · `concept_match_logs` · `user_identities`도 지워지고 다른 사용자의 데이터는 그대로다. 기존 모든 세션은 사용할 수 없다. `llm_calls` 의 비용 기록은 남되 탈퇴한 사용자 · 작업으로 연결되지 않는다 |
| **탈퇴와 자료 완료 경합** — 완료 트랜잭션 먼저 · 탈퇴 먼저 · 동시 실행 | 교착 없음. 어느 순서든 그 사용자의 개념 · 카드 · 판정 기록이 남지 않는다(완료가 먼저면 탈퇴가 함께 지우고, 탈퇴가 먼저면 완료가 `0 rows` 로 롤백) |
| **탈퇴와 평가 저장 경합** — 평가 먼저 · 탈퇴 먼저 · 동시 실행 | 복습 락으로 직렬화되어 교착 · FK 오류 없이 탈퇴가 끝난다. 평가가 먼저면 그 복습 기록까지 지워지고, 탈퇴가 먼저면 평가는 `404` |
| **탈퇴와 비용 기록 경합** — 기록 먼저 · 탈퇴 먼저 · 동시 실행, 탈퇴 뒤 늦은 응답 | 모든 순서에서 그 시도는 원장에 한 번 확정되고 전역 합계 쿼리에 잡힌다. 사용자 합계 쿼리에서는 빠지고 학습 데이터는 삭제, 호출 기록의 계정 · 잡 · 프로바이더 요청 ID 연결은 해제. 늦은 기록이 연결을 되살리지 않는다 |
| **일일 합계 쿼리** — 확정 · 미확인 · 다른 날짜 · 탈퇴로 `user_id` 가 빈 행 | 사용자 합계는 그 사용자의 오늘 `KNOWN` 만, 전역 합계는 오늘 `KNOWN` 전부(빈 `user_id` 포함). 자정 전 등록 · 자정 뒤 확정은 등록 날짜로 더해진다 |
| **외부 재시도와 DB 재시도 구분** — 채팅 · 임베딩 각각 | 실제 외부 재전송은 다른 시도 ID로 기록하고 각각의 확인된 사용량을 합산. 같은 결과의 DB 기록 재시도는 같은 ID이며 추가 합산 없음 |
| **처음부터 다시 만들기 규칙** — 대상 코드 · 다른 실패 코드 · 같은 날 3번째 `restart` · 동시 `restart` 둘 · 킬스위치/쿼터/진행 중 2개 | 두 코드에서만 새 잡. 다른 실패 코드면 `restart` 를 무시하고 일반 재시도. 같은 날 3번째는 `409 LESSON_RESTART_LIMIT`(`Retry-After` = 한국 자정까지). 동시 요청은 새 잡 하나. 검사에 걸리면 새 요청과 같은 `429` · `503` |
| **다시 만들기 하루 경계** — 한국 자정 직전 2번 · 자정 직후 1번 · UTC 자정 전후 | 한국 날짜로 센다 — 자정 직후에는 다시 만들 수 있다. 실패한 채 남은 강의는 `nextLesson` 이 건너뛰지 않고, 자료 없이 두 코드로 실패한 동안 U6 `stuckLessons` 에 센다 |
| **다시 짜기 하루 한도** — 같은 날 4번째 다시 짜기 · 한국 자정 뒤 · 실패한 다시 짜기 잡의 재시도 · 최초 생성 잡 | 4번째는 `409 REGENERATION_LIMIT`(`Retry-After` = 한국 자정까지), 자정 뒤에는 다시 가능. 재시도는 같은 행이라 횟수를 쓰지 않고, 최초 생성 잡은 다시 짜기로 세지 않는다. 횟수 컬럼 없이 잡 행에서 센다 |
| **누적 호출 상한** — 작업 A/B · 채팅/임베딩 · 설정 변경 | 초기값 A 채팅 6회 · 검색 임베딩 4회, B 채팅 24회 · 임베딩 40회. 종류별 몫을 빌려 쓰지 않으며 기존 잡의 상한은 설정 변경으로 늘지 않는다. 임베딩 상한 소진을 empty로 삼키지 않는다 |
| **숙련도 검색 범위** — 미학습 사전 항목 · 다른 사용자 · 생성만 한 카드 · 높은 R의 무관 개념 | 후보는 본인이 학습 완료한 개념만. `R` 순 500개 제한으로 관련 개념을 미리 버리지 않는다. 후보 없음은 검색 임베딩 호출 0회 |
| **숙련도 검색 합산** — 동의어 · 동명이의 · NULL/다른 모델/차원 벡터 · 동점 | 의미 검색의 별도 임계값 · 키워드 순위 · 합산식 · ID 동점 규칙대로 결정. 같은 ID만 중복 제거하고 같은 이름의 다른 개념은 보존. NULL 벡터는 키워드 경로로 검색 가능. 카드 연결 · 개념 생성 · 매칭 로그에 쓰기 0회 |

| **단계 완료 후 다음 생성 안내** — 마지막 강의 완료 · 복습 카드 남음 · 마지막 단계 | `COMPLETED` 뒤 다음 단계 생성 버튼 표시. 남은 복습이나 `R/S`로 막지 않으며 완료 이벤트의 유료 호출/새 잡 0회. 마지막 단계면 전체 완료 안내. 앞 단계 미완료 중에는 같은 분할안의 다음 단계 생성 불가이며 독립 주제 생성은 기존대로 가능 |
| **다음 단계 중복/복귀** — 두 탭 동시 클릭 · 생성 응답 유실 · 새로고침/재로그인 · 잡 실패 | 같은 단계의 커리큘럼/활성 잡 하나. 서버에 보존된 분할안/연결로 복귀하고 이미 생성한 단계는 다시 만들지 않음. 실패 재시도와 쿼터 거절 뒤에도 다음 단계 진입점 유지 |
| **다음 단계 숙련도 시점** — 분할안 저장 뒤 학습/복습 · 다음 단계 새 생성 · 동일 잡 재개 | 새 단계 생성 시 최신 숙련도로 새로 선별하며 이전 단계/분할 시점 스냅숏 재사용 없음. 동일 잡 재개만 자신의 선별 체크포인트를 재사용. 실제 분할 범위/중복/선행 관계의 적절성은 콘텐츠 수동 채점 대상으로 남김 |
| **묶음 삭제 · 단계 커리큘럼 삭제** — 단계 짜는 중 묶음 삭제 · 학습 중 단계 삭제 뒤 다시 만들기 · 앞 단계 삭제 뒤 다음 단계 만들기 · 삭제 뒤 늦은 워커 응답 | 묶음 삭제는 연결 커리큘럼의 강의 · 자료 · 플래시카드 · 복습 이력 · 연결 잡과 단계 · 묶음을 한 트랜잭션으로 지우고 생성 비용 기록은 남김. 단계 커리큘럼을 지우면 그 단계는 미생성으로 조회되고 생성 조건(1단계 · 직전 단계 `COMPLETED`)을 다시 따름 — 뒤 단계는 그대로. 늦은 응답이 묶음 · 단계 · 커리큘럼을 복원하지 않음. 아직 실행 결과가 아님 |
| **실패한 초기 요청 지우기** — 실패 · 짜는 중 · 성공한 요청 · 남의 요청 | `FAILED` 만 지워지고 원장의 사용량은 남으며 잡 연결만 풀린다. 짜는 중 · 성공은 `409 JOB_NOT_FAILED`, 남의 것은 `404`. 지운 뒤 같은 요청 ID 의 재전송 처리는 요청 식별자 TASK 에서 함께 검증. 아직 실행 결과가 아님 |
| **강의 수 경계** — 스텁 출력 0 · 1 · 40 · 41강 | 1강/40강은 나머지 검증 통과 시 저장 가능. 0강/41강은 기존 수정 몫 안에서 수정하고 여전히 위반하면 `LLM_OUTPUT_INVALID`. 주당 최소/최대 강의 수 검사는 없음 |
| **학습 일정 제외 · 자유 진도** — 주제/목적 또는 다시 짜기 피드백의 일정 요청 · 뒤 강의 먼저 열기 | 생성 지침은 일정/완료 기간을 약속하지 않고 함께 적힌 내용/범위 변경만 반영. 승인 후 앞 강의 미완료나 날짜를 이유로 뒤 강의를 막지 않음. 실제 생성이 지침을 따르는지는 콘텐츠 수동 채점에서 확인하며 구조 테스트로 보장했다고 쓰지 않음 |
| **승인 조건** — 초기 생성 실패 · 단계 최초 생성 실패 · 빈/구조 위반 출력 · 활성 잡 · 성공한 목록 | 초기 실패는 실제 커리큘럼 없음. 단계 생성 실패의 빈 초안은 `409 CURRICULUM_NOT_READY`, 잘못된 출력은 기존 수정 몫 후 `LLM_OUTPUT_INVALID` 이며 저장/승인 불가. 활성 잡은 `409 CURRICULUM_GENERATING`. 검증된 목록과 활성 잡 없음이면 `ACTIVE` 로 전환 |
| **다시 짜기 실패 후 승인** — 이전 성공 목록이 있는 상태에서 생성/저장 실패 | 이전 제목 · 강의 · 숙련도 반영/선별 근거 보존. 최근 잡이 `FAILED` 여도 이전 안을 승인 가능. U3에 이전 목록과 시작 버튼 표시 |
| **승인과 다시 짜기/재시도 경합** — 실제 PostgreSQL에서 두 요청 동시 실행 | 같은 커리큘럼 잠금으로 직렬화. 승인 먼저면 다시 짜기 `409 CURRICULUM_NOT_DRAFT`, 실패 잡 재시도 `409 JOB_NOT_RETRYABLE`. 적재 먼저면 승인 `409 CURRICULUM_GENERATING`. `ACTIVE` 와 활성 잡 A가 함께 생기지 않음 |
| **잡 A 완료와 승인 경합 · 완료 롤백** | 결과 교체와 `SUCCEEDED` 가 원자적. 승인 전에 온전한 검증 목록을 읽거나 활성 잡으로 거절. `DRAFT` 가 아니면 결과 교체를 롤백하며 승인된 목록을 덮어쓰지 않음 |
| **주제 거절**(스텁 거절 출력) | 재요청 0회 · `TOPIC_REJECTED` · 재시도 API `409 JOB_NOT_RETRYABLE` |
| **알림 하루 한 번** — 같은 이벤트 둘(웹훅 스텁) | 슬랙 전송 1회 · 웹훅 실패가 잡을 실패시키지 않는다 |
| **세션** — 기기 둘로 로그인 후 한쪽 로그아웃 · 탈퇴 · 대기자 승인 | 로그아웃한 쪽만 `401` · 다른 쪽 유지 / 탈퇴 후 **모든 세션 `401`** / 승인 직후 **다음 요청부터** `ACTIVE`(세션에 상태를 들고 있지 않다) |
| **429 백오프**(스텁 주입) | `retry-after` 존중 · 지터 · 상한 60초 · `insufficient_quota` 는 즉시 실패 |
| **개념 매칭** — 정해 둔 쌍(동의어 · 동명이의 · 유사 개념) | 임계값 0.46 / 0.78 로 기대대로 합치고 가른다(임베딩은 고정 벡터로) |
| **임베딩 실패** — 재시도 소진 · 같은 이름의 기존 개념이 하나 또는 여러 개 있음 | 기존 개념에 연결하지 않고 이름 · 정의를 보존한 별도 개념(`embedding=NULL`)에 카드를 연결. 기존 카드와 숙련도는 변하지 않고 자료 생성은 성공. `EMBEDDING_UNAVAILABLE` 기록과 `concept.embedding.missing` 계측 |
| **임베딩 실패 이후 매칭** — NULL 개념이 있는 상태에서 새 임베딩 생성 성공 | NULL 개념은 유사도 비교에서 제외하고 이름만으로 연결하지 않는다. 비교 가능한 후보에 대해서만 임계값을 적용 |
| **개념 사전 사용자 격리** — 두 사용자가 같은 이름 · 정의의 개념을 만든다 | 개념 두 행. 서로 연결되지 않고 매칭 · `lookupMastery` · 선별이 다른 사용자의 개념을 보지 않는다. 서로의 개념 쓰기 락을 기다리지 않는다 |
| **같은 사용자의 동시 완료** — 진행 중 잡 둘이 같은 새 개념으로 동시에 완료 | 사용자 락으로 직렬화되어 개념 한 행, 두 번째 판정은 연결 |
| **판정 기록의 들어온 값** — 연결 · 새로 만듦 · 동명이의 분리 · 임베딩 실패 | 모든 분기에서 `material_id` · `input_name` · `input_name_normalized` · `input_definition` 이 채워진다 |
| **별칭 조회** — `Opportunity Cost` 로 만든 개념에 `기회비용` 카드가 연결된 뒤 `lookupMastery("기회비용")` | `matched=true` 로 그 개념과 판정을 돌려준다. 연결된 적 없는 표기는 `matched=false` |
| **미학습 개념 조회** — 자료만 생성하고 학습 완료하지 않은 카드의 개념 이름으로 조회 | `matched=false` · `DETAIL`. 학습 완료하면 `matched=true` |
| **병합 후 별칭** — 병합 SQL 실행 후 `:drop` 의 이름으로 조회 · 새 카드 | 조회는 `:keep` 을 돌려준다. 그 이름의 새 카드는 이름 같음 분기(0.46)로 `:keep` 에 연결되고 새 개념을 만들지 않는다. 판정 기록은 지워지지 않고 `:keep` 으로 옮겨지며 `corrected_at` 이 찍힌다. 다른 사용자의 개념이 섞인 병합은 확인 단계에서 2행이 아니라 멈춘다 |
| **되돌리기** — 정보이론 `엔트로피` 가 열역학 `엔트로피` 에 잘못 연결된 판정을 되돌린 뒤, 두 분야의 `엔트로피` 카드가 새로 들어온다 | 새 개념은 들어온 이름 · 정의 · 벡터를 갖는다. 고른 카드만 옮겨지고 숙련도가 갈린다. 다음 카드는 각자 정의가 가까운 개념에 연결된다(같은 실수 반복 없음). 판정 기록은 새 개념으로 옮겨지고 `corrected_at` 이 찍힌다 |
| **되돌리기 후 별칭** — `명목금리` 가 `실질금리` 에 잘못 연결된 판정을 되돌린 뒤 `명목금리` 로 조회 · 새 카드 | `실질금리` 로 끌려가지 않고 새 `명목금리` 개념으로 간다 |
| **연결 판정의 벡터** — 연결 · 새로 만듦 · 동명이의 분리 · 임베딩 실패 | `LINKED` 만 `input_embedding` 이 채워지고 나머지는 NULL |
| **병합 · 되돌리기 전제** — 그 사용자에게 `QUEUED` · `RUNNING` 잡이 있을 때 | 확인 쿼리가 0 이 아니라 진행하지 않는다 |
| **SKIP 개념 카드 금지** — 개요에서 `SKIP` 인 개념의 카드를 스텁이 낸다 | 그 카드는 저장되지 않고 나머지 카드는 저장된다. `cards.dropped{reason=skip_concept}` +1. 학습 완료 뒤 그 개념의 `minReviewCount` 가 그대로라 다음 강의에서도 `SKIP` |
| **SKIP 카드와 임베딩 실패** — `SKIP` 개념과 같은 이름(또는 별칭)의 카드 · 다른 이름의 카드, 둘 다 정의 임베딩 실패 | 같은 이름 카드는 별도 개념을 만들지 않고 버린다(`cards.dropped{reason=skip_concept}`). 다른 이름 카드는 기존 규칙대로 `embedding=NULL` 별도 개념에 연결 · `EMBEDDING_UNAVAILABLE` 기록 |
| **카드 단계 개념 목록** — 학습자가 가진 개념 · 가지지 않은 개념이 섞인 개요 | ③ 입력에 `matched=true` 개념의 이름 · 판정만 들어간다. 목록의 이름을 쓴 카드는 이름 같음 분기로 연결된다. ③ 재개 때는 저장된 `masteryFindings` 로 같은 목록을 만든다 |
| **별칭 매칭과 동명이의** — `인플레이션` 에 별칭 `inflation` 이 있는 상태에서 경제 정의의 `inflation` · 우주론 정의의 `inflation` 카드 | 경제 쪽은 이름 같음 분기로 연결, 우주론 쪽은 유사도 0.46 아래라 새 개념(`SPLIT`) |
| **사용자 락 종류 키** — enqueue · usage-user · review · concept-write | 첫 키(`hashtext` 값)가 서로 다르다 |
| **잡 시한** — 10분 넘긴 잡 | 수령 직후 · 시도 경계에서 `DEADLINE_EXCEEDED` |
| **역할별 기동** — `all` · `api` · `worker` 로 각각 컨텍스트를 띄운다 | `api` 에 수령 루프가 없고 `worker` 에 컨트롤러가 없다 · `api` 와 `worker` 를 함께 띄워 잡 하나가 끝까지 도는지(비상용 배선이 실제로 동작하는지) |

### 1.3 숙련도 선별 품질 — 공개 후 측정해 검색 설정을 확정한다

**공개 후에 한다**([ADR-057](./ADR.md)). 그전까지 잡 I · A 는 잠정 설정 버전으로 동작한다([02 §5.4](./02-domain-data.md)).

주제 · 학습 목적별로 가상의 사용자 학습 개념 목록과 기대 관련 개념을 수동 라벨링한다. 동의어, 동명이의, 선수 개념, 넓은 주제, 관련 이력이 없는 경우, NULL/다른 모델 벡터를 포함한다. 임계값 · 후보 수를 고르는 자료와 마지막 평가 자료를 나누며, 개념 동일성의 47쌍 실험을 검색 평가로 대신하지 않는다.

같은 사용자 이력 · 같은 목표에서 전량 주입, 키워드 단독, 임베딩 + 키워드 선별을 비교한다. 후보 수 · 검색 임계값 · 주입 바이트 예산을 바꾸어 필요한 개념의 재현율, 무관한 개념의 포함 비율, 전체 입력 크기 · 상한 거절률, 검색 지연과 추가 임베딩 비용을 기록한다. 전량 요청이 입력 상한을 넘으면 거절된 비교군으로 기록하고, 제한을 풀어 생성한 결과와 섞지 않는다. 라벨 자체의 한계도 보고한다.

개념 누락으로 이미 아는 내용을 다시 설명하는 경우와 잘못 참조한 숙련도로 필요한 내용을 생략하는 경우를 따로 평가한다. 생성 콘텐츠에서도 필요한 선수 개념이 유지되는지 확인한다. 합산 규칙 · 불용어 목록 · 토크나이저/임베딩 모델 · 프롬프트/코드 버전 · 선택한 ID와 검색 순위 · 입력 크기 · 원장 사용량 · 표본 수를 함께 남긴다.

평가 전 통과 기준을 정하고, 그 결과로 `selectionLimit` · `semanticMinSimilarity` · 주입 예산을 확정한다. **아직 측정값이나 확정 숫자는 없다.** 코드의 후보 범위/정렬 규칙 테스트 통과만으로 콘텐츠 관련성이나 비용 절감을 달성했다고 주장하지 않는다.

### 1.4 공개 전 콘텐츠 품질 — 실제 생성 결과 수동 검증

공개 통과선은 [01 §9](./01-overview.md)에 따른다. 제작자가 아는 분야 2~3개의 검증 표본 강의 **10개 전체**를 채점하고, **치명 결함 0개 · 점수 평균 1.5 이상 · 항목별 평균 1.0 이상**을 모두 충족해야 공개할 수 있다. 코드 스텁/구조 검사 통과를 실제 콘텐츠 품질 검증으로 대체하지 않는다.

숙련도 **미반영/반영 결과를 비교해 개인화 효과를 검증하는 실험은 우선 계획에 추가하지 않는다**(사용자 결정). §1.3의 전량 주입/키워드/임베딩 검색 방식 비교는 공개 후에([ADR-057](./ADR.md)), 이 절의 공개 전 수동 품질 채점은 기존대로 수행한다.

- K1~K3 중 하나라도 발견하면 점수 평균과 관계없이 불합격이다. 표본이 10개 미만이거나 대조 확인을 마치지 않은 상태는 통과가 아니다.
- 결함을 발견해 프롬프트 · 모델 · 생성/후처리 구성을 고친 뒤에는 새 표본 10개를 생성해 다시 채점한다. 실패 강의를 제외하거나 수동 수정한 강의만 재채점해 통과시키지 않는다.
- 이전 실패 결과와 새로운 결과를 구분해 보존한다. 기존 CSV에 강의 ID · 모델 · 프롬프트 버전 · 결함 유무/점수 · 대조 근거/메모를 남긴다. 실제 채점을 수행하기 전에는 검증 완료로 기록하지 않는다.

## 2. 용량 측정 — 정원을 정한다

**질문 하나** — *"EC2 한 대로 동시에 몇 명이 써도 생성 대기와 복습이 견딜 만한가."* 답이 정원 `U_max` 의 한쪽이고, 예산 쪽(약 25명)과 비교해 **작은 쪽**을 쓴다.

| 항목 | 내용 |
|---|---|
| 환경 | 로컬 Docker Compose · **운영과 같은 메모리 조건으로 묶는다** · Postgres · LLM 스텁(§3). **측정 전에 Postgres 위치를 정한다**([04 §3](./04-jobs-and-cost.md)) — 같은 인스턴스면 앱 + Postgres 를 **합쳐서** 인스턴스 크기로 묶고, RDS 면 앱 컨테이너만 묶는다. 위치를 정하지 않고 재면 그 숫자로 정원을 정하지 않는다 |
| 가상 사용자 | `POST /dev/session` 으로 만든다(`loadtest` 프로필 · k6 쿠키 저장소) |
| 사용 패턴(**가정 — 리포트에 명시**) | 활성 사용자 1명이 저녁 몰리는 시간에: 강의 1개 열기(생성 + 2초 폴링) → 읽기 → 학습 완료 → 첫 복습 → 오늘의 복습 20~30장. 가끔 커리큘럼 생성 · 다시 짜기 |
| 늘리는 것 | 동시 활성 사용자 수 · 실행기 `N` |
| 보는 것 | 생성 대기(적재 → 수령) p50 · p95 · 강의 1건 전체 시간 · **복습 API p99** · 폴링 요청 수 · **요청마다 붙는 세션 조회 · 갱신** · JVM 힙 · RSS · GC · DB 커넥션 대기 · CPU |
| 결과 | *"`N` = ⟨ ⟩, 동시 ⟨ ⟩명까지 생성 대기 p95 ⟨ ⟩ · 복습 p99 ⟨ ⟩ · 메모리 ⟨ ⟩"* → `N` · 워커 폴링 주기 · 정원 확정 |

- 🅿️ **통과 기준은 측정 전에 정한다**(잠정 제안 — 생성 대기 p95 ≤ 2분 · 복습 API p99 ≤ 300ms · 메모리가 인스턴스 크기 안에서 안정).
- 공개 후 **실제 사용 패턴으로 가정을 검증**한다. 어긋나면 정원을 다시 계산한다.
- 실서버(AWS)에 부하를 걸지 않는다 — 실사용자 영향 · 계정 제재.

**측정 조건 카드** — 숫자 하나에 조건을 붙인다. 조건 없는 숫자는 첫 질문에 무너진다.

```
커밋 해시 | k6 시나리오 · 가상 사용자 수 · 지속 시간 | N · 커넥션 풀 크기 · 워커 폴링 주기
스텁 프로파일 · 시드 · 꼬리 · 429 주입 여부(가정 명시) | 컨테이너 크기(CPU · 메모리) | 예상과 다른 점
```

## 3. LLM 스텁 서버

실제 API 에 부하를 걸면 비용이 나가고 계정이 막힌다. 스텁은 **1단계에서 잰 지연 · 토큰 · 호출 패턴**을 흉내 낸다 — 그래야 부하 테스트의 숫자가 지어낸 숫자가 아니다.

### 3.1 흉내 낼 분포 (OpenAI · 1단계 v5 실험 프롬프트 · 실측 6~18회)

> ⚠️ 아래 분포는 실험 프롬프트로 잰 값이다. 운영 프롬프트(`src/main/resources/prompts/v6/`)를 만들면 같은 방식으로 다시 재서 이 표를 바꾸고, **용량 측정은 그 뒤에** 한다 — 실험 프롬프트 분포로 잰 정원은 운영과 다르다.

| 단계 | 모델 | 지연 p50 · p95 · 최대 | 출력 토큰 p50 · 최대 | 출력 속도 |
|---|---|---|---|---|
| ① 1회째(툴 호출) | terra | 2~3s | 150~250 | — |
| ① 2회째(결론) | terra | 3~7s | 300~720 | — |
| ② 본문 | terra | 31.8 · 34.9 · 34.9s | 3,042 · 3,603 | 약 100 토큰/초 |
| ③ 카드 | luna | 17.4 · 20.4 · 21.2s | 2,434 · 2,587 | 약 140 토큰/초 |
| 잡 A | terra | 15.9 · 23.5 · 24.4s | 2,181 · 2,258 | — |

**지연은 출력 토큰이 정한다** — 출력 토큰을 먼저 뽑고 지연을 계산한다(상한을 바꾸는 실험에서도 지연이 따라온다).

```
출력 토큰 ~ 균등[p50 × 0.8, 최대]
지연(초)  = 0.5 + 출력 토큰 ÷ 출력 속도 × (1 + 정규잡음(0, 0.08))
```

잡 B 호출 패턴 — 실측 15건 모두 **4회**(① 2 · ② 1 · ③ 1). 상한(8회) 근처는 실측에서 안 나왔다 — 보고 싶으면 §3.3 주입으로 만든다.

### 3.2 꼬리 — 잰 것이 아니라 가정이다

| 꼬리 | 비율 | |
|---|---|---|
| 느린 응답(지연 × 2~3) | 2% | 실측 0/67. 없으면 타임아웃 · 리스 경로가 한 번도 안 돈다 |
| 응답 없이 붙잡기(타임아웃) | 0.5% | 재시도 경로를 태우려고 |
| 5xx | 0.5% | |

리포트에 **가정으로 표시한다.**

### 3.3 주입 — 시험별 설정

| 주입 | 설정 | 쓰는 곳 |
|---|---|---|
| 429 + `retry-after` | `stub.rpm` · `stub.tpm` · `stub.quotaExhausted` | 백오프 · `insufficient_quota` 즉시 실패 검증 |
| 한도 헤더 | 응답마다 `x-ratelimit-remaining-*` · `reset-*` | `llm.ratelimit.remaining` 게이지 |
| ① 라운드 늘리기 | `stub.outlineRounds=1..3` | 잡 최대 호출 경로 · 강제 종결 |
| 잘림 | `stub.truncateRate` → `finish_reason=length` | 이어 쓰기(장애 주입 6) |
| 파싱 깨짐 · 단계 실패 | `stub.badJsonRate` · `stub.failStep` | 재요청 · 단계 재개(장애 주입 7) |
| 초기 잡 I/잡 A 거절 | `stub.rejectTopic` → `{"rejected": true, …}` | `TOPIC_REJECTED` · 재요청 0회 |

### 3.4 응답 모양

- **OpenAI Chat Completions 형식** 그대로 — 서비스의 어댑터를 그대로 쓰고 SDK `baseUrl` 만 스텁으로 돌린다.
- 본문은 의미 없어도 된다 — **길이와 형식**만: 정상 ② 응답은 6섹션 제목과 비어 있지 않은 섹션별 더미 내용을 갖추고 정상 종료한다. 잘림/빈 섹션 주입은 정상 응답과 구분한다. ③은 카드 JSON 10장, ①은 `tool_calls` → 결론 JSON. `usage` 를 채운다.
- 임베딩 엔드포인트도 흉내 낸다(고정 차원 · 시드 기반 벡터).
- **`stub.seed`** — 같은 시드면 같은 지연 순서. 측정을 다시 돌려도 같은 조건.

**이 명세가 틀리는 경우** — 표본이 작아 분포 모양을 모른다(범위만 흉내 낸다) · 시간대별 지연 변화를 모른다 · 스텁은 붐벼도 느려지지 않는다(의도 — 측정 대상은 *우리 서버*다).
실사용 호출 기록이 쌓이면 §3.1 표를 그 값으로 바꾼다.

## 4. 실사용 운영 기록 — 주 1회 스냅숏

포트폴리오의 실사용 증거다. 지나가면 복구할 수 없어서 **본인 실사용을 시작한 주부터** 남긴다.

| 생성 요청 수 · **기존 잡에 연결된 수**(막은 중복) | API 메트릭 |
| 작업별 실패 이력 · **재개된 단계**와 그 앞 단계의 관측 사용량 기반 비용(→ *아낀 돈*, 계산값으로 표시) | `job_events` · `jobs` · `llm_calls` · 메트릭 |

| 사용량 미확인 호출 | `llm_calls` 의 `UNKNOWN` + 시한 지난 `PENDING`. `llm.call.no_usage` 는 프로세스가 관측한 일부 경로의 메트릭 |
| 회수 · 반납 · 펜싱 | 최근 회수 이력은 `job_events`; 반납/펜싱은 `job.released` · `job.write.fenced` 메트릭/로그. 영속 24시간 지표로 대신 쓰지 않음 |

| 429 · 한도 헤더 여유 | 레이트리미터 트리거 확인 |
| 개념 판정(합침 · 가름 · 새로 만듦 · 경계) · 수동 병합 · **이름이 다른데 연결된 건수**(표기 규칙이 통하는가) | `concept_match_logs` · 작업 일지 |
