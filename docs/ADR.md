# Architecture Decision Records

> **지금 유효한 결정만** 있다. 대체된 결정은 번호와 대체한 결정 한 줄만 남긴다. 결정마다의 질문 · 대안 · 뒤집은 기록(Q1~Q231)과 1단계 실측 원자료는 기획 저장소 `f-lab-design` 에 있다
> (`docs/00-project-status.md` · `docs/13-adr/` 0001~0006 · `phase1/report.html`).
> 상세는 각 결정의 링크 — 둘이 다르면 링크한 문서가 맞다.

## 철학

- **측정으로 고르고 계산으로 자른다.** 단가표가 아니라 실측(약 225회 호출)으로 모델을 고르고, 한도 여유 · 초과 비용 · 리스는 식으로 묶는다.
- **트리거 없이 넣지 않는다.** 만들지 않는 것마다 *다시 넣는 조건*을 적고([01 §6](./01-overview.md)), 조건이 오기 전에는 넣지 않는다.
- **고장을 연출하지 않는다.** 이 규모(정원 약 25명 · 서버 한 대)에서 일어나지 않는 문제를 일부러 만들어 고치지 않는다.
- **돈이 드는 작업은 한 번만 · 끝까지.** 생성은 처음부터 비동기 잡이고, 중복 방지 · 단계 재개 · 장애 회수가 기본이다.

## 서버 · 구조

### ADR-001: 생성은 처음부터 비동기 잡 — `jobs` 테이블이 큐
**결정**: 커리큘럼 · 강의 자료 생성은 `jobs` 행으로 적재하고 워커 실행기 `N` 개가 수령한다. 화면은 `jobId` 를 2초 폴링한다.
**이유**: 처리량 때문이 아니다. 돈이 드는 1분짜리 작업을 한 번만 · 끝까지 하려면 진행 중 작업이 DB 에 있어야 한다 — 중복 방지 · 진행 중 2개 · 단계 재개 · 장애 회수. ([04 §4](./04-jobs-and-cost.md))
**트레이드오프**: 동기 호출보다 코드와 화면 상태가 많다. 정확히 한 번은 보장하지 않는다(at-least-once — 회수 시점에 이미 나간 호출 1회).

### ADR-002: 큐는 Postgres `SKIP LOCKED` · 저장소는 Postgres 하나
**결정**: Redis · Kafka 없이 PostgreSQL + pgvector 하나.
**이유**: 요구가 SQL 한 문장(수령 · 회수 · 펜싱)에 들어가고, 잡 상태와 산출물이 한 트랜잭션이다.
**트레이드오프**: 큐가 초당 수백 건이면 틀린 선택이다(hot row · VACUUM).

### ADR-003: `jobs` 는 JPA 가 아니라 명시적 SQL · 수령 회차 펜싱
**결정**: `jobs` 는 엔티티로 매핑하지 않고 모든 쓰기를 `EntityManager` 네이티브 쿼리 + `lease_epoch` 조건으로 한다. 도메인 테이블은 JPA 엔티티(ADR-042).
**이유**: 수령 회차와 일반적인 행 버전을 구분하고, 리스 유효성 · 소유권 · 상태 전이를 SQL 에 명시한다. 엔티티로 만들면 더티 체킹 · merge 가 `lease_epoch` 와 상태를 옛 값으로 덮을 수 있다. ([04 §4.4](./04-jobs-and-cost.md))
**트레이드오프**: 같은 JPA 안에서도 엔티티와 네이티브 쿼리 두 방식이 섞인다. 호출 원장의 조건부 확정도 네이티브 쿼리로 처리한다.

### ADR-004: 플랫폼 스레드 · 가상 스레드 미사용
**결정**: Spring MVC + 플랫폼 스레드. 오래 기다리는 작업은 워커 실행기 `N` 개로 묶는다.
**이유**: 기다리는 작업이 `N` 개로 묶여 있어 가상 스레드의 이득이 없다(SDK pinning 은 JFR 로 확인).
**트레이드오프**: 오래 기다리는 연결이 수백 개 동시에 생기는 기능이 오면 다시 본다.

### ADR-005: 단일 Gradle 모듈 + ArchUnit
**결정**: `core` ← `api` · `worker` · `infra` 경계를 패키지와 ArchUnit(첫 커밋)으로 강제한다. 생성 유스케이스와 유료 호출 포트(`LlmClient` · `EmbeddingClient` …)는 `core.generation` 에 모으고, 이 패키지를 참조할 수 있는 쪽을 `worker` · `infra` · 루트 설정으로 **허용 목록**으로 적는다 — api 금지만 두면 다른 core 패키지를 거친 우회를 못 막는다. 도메인 모델(record)은 `core.<도메인>` 에 둬 api 와 생성이 같이 쓴다 — JPA 엔티티는 `infra` 에만 둔다(ADR-042).
**이유**: 멀티모듈을 부를 계기(배포 단위 · 팀 · 공개 라이브러리)가 없다. 강제 결과는 같다. ([04 §2](./04-jobs-and-cost.md))
**트레이드오프**: 컴파일러가 아니라 테스트가 막는다 — 규칙을 무르면 경계가 사라진다.

### ADR-006: 한 프로세스로 운영 · 역할 전환은 비상용 배선
**결정**: `app.role=all` 하나로 돈다. `api` / `worker` 로 실행 인자만 바꿔 나눌 수 있는 배선은 처음부터 넣는다. 격리 실험 · 대조 실험은 하지 않는다. *(Q221 · Q233)*
**이유**: 운영이 한 대 · 한 프로세스다. 배선은 수십 줄로 *장애 때 실행 인자만 바꿔 나누기* 를 산다. ([04 §3.1](./04-jobs-and-cost.md))
**트레이드오프**: 트리거 없이 미리 만드는 유일한 예외다. 워커가 API 지연에 영향을 주는 게 관측되면 나눈다.

### ADR-007: 화면은 React SPA 를 Spring Boot 에 넣어 jar 하나로
**결정**: `frontend/`(React · TypeScript · Vite · React Router · TanStack Query · Tailwind) 빌드 결과를 `static/` 에 넣는다. 프론트 테스트는 Vitest + Testing Library, E2E 없음.
**이유**: 같은 사이트라 쿠키 세션 · CSRF(`SameSite=Lax` · `XSRF-TOKEN`)가 그대로 돌고, 1GB 서버 · 프로세스 하나 전제를 바꾸지 않는다. Next.js 는 Node 서버가 하나 더 필요하다.
**트레이드오프**: SSR · 검색 노출이 없다 — 로그인 뒤에 쓰는 앱이라 받아들인다.

### ADR-008: 주기 작업은 허용 · 파생값 저장은 금지
**결정**: 스케줄러 · 배치를 금지하지 않는다. 다만 **파생값(숙련도 · `GENERATING` 상태)은 저장하지 않는다** — 조회 때 계산하거나 잡으로 판단한다.
**이유**: 처음엔 배치 일체를 금지했지만, 정합성을 지키는 것은 *파생값을 저장하지 않는* 규칙이었다. 백업(`pg_dump`) 같은 운영 작업까지 막을 이유가 없다. 이미 배치 없이 짠 것(수령 쿼리의 회수 · 날짜 비교 리셋 · 완료 시 `payload` 비우기)은 그 자체로 단순해서 그대로 둔다.
**트레이드오프**: 주기 작업을 넣을 때 역할 전환 후 두 번 돌아도 되는지(멱등)를 매번 정해야 한다.

### ADR-009: 슬롯 세마포어 없음 — 실행기 `N` 이 곧 동시 호출 상한
**결정**: 별도 세마포어를 두지 않는다. 모든 LLM 호출에 `JobRef` 가 필수다. *(Q224)*
**이유**: 잡 없는 호출(옛 v1 · v2)이 없어졌고, 실행기 ≤ `N` 이면 세마포어는 대기 0 이다.
**트레이드오프**: 잡 밖에서 LLM 을 부르는 기능이 생기면 다시 본다.

## 인증

### ADR-010: 쿠키 세션 + Spring Session JDBC (JWT 아님)
**결정**: 구글 OAuth + Postgres 저장 쿠키 세션 · 비활동 7일 만료 · 세션에는 사용자 id 만.
**이유**: 로그아웃 · 탈퇴 즉시 반영과 대기 · 약관 상태 확인 때문에 어차피 요청마다 DB 를 본다 — JWT 의 이점이 없고 코드만 는다. 기기별 로그아웃 · 배포 · 프로세스 분리에도 유지된다. ([05 §1.1](./05-api.md))
**트레이드오프**: 모바일 앱 · 다른 도메인 서비스가 같은 인증을 써야 하면 다시 본다.

## LLM

### ADR-011: Spring AI 대신 OpenAI SDK + 자체 포트
**결정**: `LlmClient`(1턴) · `GuardedLlmClient`(재시도 · usage · 리스 갱신) · SDK `maxRetries(0)`.
**이유**: 재시도 · 리스 갱신을 시도 단위로 쥐어야 리스 부등식(`300 > 60 + 100 + DB 처리 최대 지연`)이 선다. 프레임워크 안에 숨으면 확인할 수 없다. ([03 §8](./03-generation.md))
**트레이드오프**: 프로바이더를 상시 여럿 지원하려면 어댑터를 직접 늘려야 한다.

### ADR-012: 채팅 OpenAI(`gpt-5.6-terra` · `gpt-5.6-luna`)
**결정**: 중상위 terra(잡 A · ① · ②) · 하위 luna(③ 카드). 포트는 모델명이 아니라 `ModelTier` 를 받는다.
**이유**: 한국어를 토큰 절반 가까이로 써서 강의 1건 **82원 vs 162원**, 46~62초 vs 74~90초. 단가표로는 반대 결론이었다.
**트레이드오프**: 품질은 블라인드 채점하지 않았다. 카드 품질(C1~C5)이 낮으면 ③을 중상위로 올린다.

### ADR-013: 임베딩 `text-embedding-3-large` · 임계값 0.46 / 0.78
**결정**: 한 줄 *정의*를 임베딩한다. 이름이 같으면 0.46, 다르면 0.78 이상일 때 같은 개념. 임베딩 실패 시에는 이름만으로 연결하지 않고 `embedding=NULL`인 별도 개념을 만들어 자료 생성을 계속한다.
**이유**: 47쌍 · 모델 4개 중 두 분기를 모두 완전히 가른 유일한 모델. ([02 §5](./02-domain-data.md))
**트레이드오프**: 표본이 작다 — 표기 쌍이 가끔 갈리고, 실사용 판정 기록으로 다시 계산한다. 임베딩 장애 때는 잘못된 병합으로 숙련도가 섞이는 일을 피하기 위해 중복을 허용한다. 이름 · 정의와 실패 분기를 남겨 나중에 검토 · 수동 병합한다.

### ADR-014: 다룰 수 없는 주제는 초기 잡 I · 잡 A 의 정식 거절 출력으로
**결정**: 초기 잡 I · 잡 A 출력에 `{"rejected": true, "reason": …}` 를 두고, 오면 재요청 없이 `TOPIC_REJECTED`(다시 시도 ❌). 입력 길이 상한(주제 100 · 목적 200 · 피드백 500자) · *"사용자 입력은 데이터"* 규칙. ([03 §2](./03-generation.md))
**이유**: 거절이 파싱 실패로 처리되면 재요청 1회 + 사용자의 「다시 시도」 가 같은 주제로 매번 돈을 쓴다. 추가 호출 없이 연습형 주제도 같은 경로로 거른다.
**트레이드오프**: 모델의 판단에 기댄다. Moderation API 는 거절을 피한 부적절한 자료가 관측되면 넣는다.

## 학습 · 복습

### ADR-015: 숙련도는 저장하지 않는다 · `R` 과 `S` 의 AND
**결정**: `card_states` 만 저장하고 숙련도(`R` 평균 · `S` 평균 · `minReviewCount`)는 조회 때 SQL 로 계산한다. 평균은 복습한 카드만, 최소 복습 횟수는 학습 완료한 모든 카드(미복습 포함)로 계산한다. `SKIP` · `EXCLUDED` 는 모든 대상 카드가 최소 2회 복습되고 `R` · `S` 조건도 충족할 때만 허용한다.
**이유**: `R` 은 시간 함수라 저장하면 낡는다. 복습 직후엔 누구나 `R ≈ 1` 이라 `S` · 복습 횟수와 함께 판정한다. ([02 §4](./02-domain-data.md))
**판정 책임**: SQL 집계 뒤 공통 `MasteryPolicy` 가 설명 깊이 · 커리큘럼 반영 방식을 결정한다. LLM 은 조회할 개념과 문맥을 선택하고 전달받은 판정에 맞춰 구성한다. 잡 A의 반영 내역은 검증하고, 잡 B의 깊이 · 목표 분량은 백엔드가 채운 뒤 본문을 생성한다. 수치 경계값은 LLM 없이 테스트할 수 있다. 자연어 내용이 판정에 맞는지는 별도 품질 채점으로 확인한다.
**트레이드오프**: `R` 공식이 라이브러리 · SQL 두 곳에 있다 — 일치 테스트가 단일 출처다. 새 강의를 학습 완료해 미복습 카드가 추가되면 이미 아는 개념도 한동안 생략되지 않는다. 일부 카드의 복습 기록만으로 개념 전체를 안다고 판단하는 일을 막기 위한 선택이다. `SKIP` 으로 다룬 강의는 그 개념의 카드를 만들지 않아 생략이 스스로 풀리지 않는다(ADR-031).

### ADR-016: FSRS 단기 학습 단계를 끈다 · 오늘의 복습은 한국 날짜 기준
**결정**: 학습 · 재학습 단계를 비워 간격을 일 단위(최소 1일)로 둔다. 간격은 라이브러리가 정하고 직접 덮어쓰지 않는다. 오늘의 복습은 `next_review_at < 내일 00:00 Asia/Seoul`.
**이유**: *하루 한 번 · 자투리 시간* 모델이라 분 단위 단계가 세션 구조(목록을 한 번 받는다)와 맞지 않는다. 시각으로 자르면 밤에 받은 1일 간격 카드가 다음 날 아침에 안 나온다. ([02 §4 · §8.1](./02-domain-data.md))
**트레이드오프**: `AGAIN` 카드를 같은 날 다시 보지 않는다. `io.github.open-spaced-repetition:fsrs:1.0.0` 은 학습/재학습 단계에 빈 `Duration[]` 을 지원하며, 기본 파라미터에서 새 카드의 네 평가와 복습 카드의 `AGAIN` 모두 최소 1일 간격임을 학습 테스트로 확인했다(2026-10-12).

### ADR-017: (대체됨) 그만둔 커리큘럼의 카드 유지 → ADR-035
커리큘럼은 그만두기 상태 없이 연결된 학습 기록 · 카드와 함께 완전 삭제한다(ADR-035).

## 비용 · 운영

### ADR-018: 비용은 사후 기록 + 3층 · 레이트리미터 없음
**결정**: 구조 상한 · 사용자 일일 비용 쿼터 · 진행 중 2개 · 전역 킬스위치. 검사는 적재 전에만, 기록은 호출 뒤에. 레이트리미터 대신 실행기 `N` + 429 백오프 + 한도 헤더 게이지.
**이유**: 정원과 진행 중 2개, 작업 전체 누적 호출 상한으로 호출 건수를 제한한다. 비용 초과분을 *진행 중 잡 × 잡 1건 최대비용* 으로 계산하려면 호출별 토큰 · 단가 상한이 먼저 검증되어야 한다. 실측 토큰 기준 분당 한도 여유 약 8배는 비용 최대치의 근거가 아니다. *(Q230)* ([04 §7 · §8](./04-jobs-and-cost.md))
**트레이드오프**: 상한을 정확히 지키지 못한다. 응답을 못 받거나 기록 전에 죽은 호출은 원장에 미확인으로 남으며 비용 합계에는 들어 있지 않다.

### ADR-019: 사용자 쿼터와 킬스위치는 같은 단위(원)
**결정**: 사용자 일일 쿼터를 토큰이 아니라 비용(원)으로 잰다.
**이유**: 토큰 단가가 모델 · 방향마다 달라 같은 토큰이 다른 돈이다. 같은 단위여야 *사용자당 월 비용 ≤ 예산 ÷ 정원* 을 그대로 계산한다.
**트레이드오프**: 단가표(설정)가 바뀌면 이후 호출의 같은 사용량도 다른 비용이 된다. 이미 등록한 호출에는 당시 단가 · 환율을 고정한다.

### ADR-020: 정원제 공개 · 정원 = min(예산, 측정 용량) · 휴면은 정원을 늘려 흡수
**결정**: 약관 동의 때 정원 검사, 넘으면 대기 명단 · 관리자 SQL 승인. 휴면 사용자를 내리거나 지우지 않고, 대기가 쌓이면 관리자가 `U_max` 를 늘린다.
**이유**: 비용이 사용자 수에 비례한다. 휴면 사용자는 비용을 쓰지 않으므로 늘릴 때 실제 활동 인원으로 다시 계산하면 된다.
**트레이드오프**: 정원 숫자가 *활동 인원* 을 직접 말해 주지 않는다.

### ADR-021: 알림은 슬랙 웹훅 + 외부 헬스체크
**결정**: 크레딧 소진 · 킬스위치 발동 · `LLM_REQUEST_REJECTED` 를 앱이 슬랙으로(같은 이벤트는 하루 한 번 — `alert_logs`), 앱 다운은 외부 헬스체크가 잡는다. ([04 §9.1](./04-jobs-and-cost.md))
**이유**: U6 는 들어가 봐야 보인다. 1GB 서버에 관측 에이전트를 올리지 않는다.
**트레이드오프**: 실패율 급증 같은 추세 알림은 없다 — U6 에서 본다.

### ADR-022: Postgres 위치는 용량 측정 전에 정한다
**결정**: 위치(같은 EC2 2GB · RDS · 같은 EC2 1GB)는 아직 미정. **용량 측정 전에 정하고, 측정은 운영과 같은 메모리 조건으로** 잰다. 1순위 후보는 같은 EC2 · 2GB. ([04 §3](./04-jobs-and-cost.md))
**이유**: 실제 메모리 사용량 없이 고를 근거가 없다. 다만 측정이 한쪽 위치를 몰래 가정하면 정원 숫자가 틀린다.
**트레이드오프**: 측정이 위치 결정을 기다린다.

### ADR-023: 시각 디자인 — 따뜻한 라이트 하나 · 쪽빛 · Pretendard · 중립 평가 버튼
**결정**: 미색 종이 · 먹색 글자 · 포인트 쪽빛 `#2F4B7C` · Pretendard. 평가 버튼 4개는 같은 중립 스타일. 다크 모드는 트리거 항목. ([UI_GUIDE](./UI_GUIDE.md))
**이유**: 핵심 화면이 긴 한국어 글 읽기다. 평가 버튼에 좋고 나쁨의 색을 입히면 자가평가가 부풀려져 다음 강의가 틀리게 맞춰진다.
**트레이드오프**: Anki 식 색 구분에 익숙한 사람에게 덜 직관적이다. 다크 모드 없음.

### ADR-024: 호출별 사용량 기록을 작업 결과 저장과 분리한다
**결정**: 채팅 · 임베딩의 전송 시도마다 `llm_calls` 을 먼저 등록하고, 확인된 사용량은 그 행에 조건부 UPDATE 로 한 번만 확정한다. 사용자 쿼터 · 킬스위치의 일일 합계는 저장하지 않고 조회 때 원장에서 더한다. 같은 시도의 DB 기록 재시도는 같은 ID, 실제 외부 재전송은 새 ID다. 리스 상실 · 잡 삭제와 무관하게 이미 나간 호출의 사용량을 기록한다. ([02 §6.8](./02-domain-data.md) · [03 §8.2~§8.5](./03-generation.md))
**이유**: 작업 진행 권한을 잃었다고 이미 발생한 사용량을 버리면 비용이 누락된다. 합계는 원장의 파생값이라 따로 저장하면 같은 트랜잭션 · 중복 합산 방지 · 락 순서 · 날짜 보정 · 탈퇴 때 사용자 합계만 지우기 같은 맞추는 장치가 붙는다(금지 목록 6). 원장 행 하나만 확정하면 재기록은 `0 rows` 라 중복이 없고, 하루 원장 행은 천 단위라 매번 더해도 가볍다.
**트레이드오프**: 테이블 하나와 시도 전후의 짧은 트랜잭션이 추가된다. 외부 응답과 DB 기록 사이의 장애로 사용량을 잃을 수 있어 미확인을 별도로 표시한다. 호출 자체나 과금의 정확히 한 번 실행을 보장하지 않는다. 탈퇴 시 계정 · 작업 연결을 해제하고 전역 비용 기록은 남긴다.

### ADR-025: 작업 전체의 누적 외부 호출 상한을 유지한다
**결정**: 잡 적재 시 채팅 · 임베딩 상한을 확정하고 `llm_calls` 의 등록 건수로 검사한다. 초기값은 A 채팅 6회 · 검색용 임베딩 4회(ADR-027), B 채팅 24회 · 임베딩 40회다. 등록 트랜잭션의 잡 행 잠금으로 검사와 삽입을 직렬화한다. 서버 재시작 · 리스 회수 · 반납 · 사용자 재시도에도 이력과 상한을 유지한다. 소진 뒤 추가 호출이 필요하면 `JOB_CALL_LIMIT_EXCEEDED`, 같은 잡의 재시도는 거절한다. ([04 §4.8](./04-jobs-and-cost.md))
**이유**: 실행기 메모리의 재시도 횟수와 일일 쿼터만으로는 반복 장애 · 사용량 미확인 · 날짜 변경 때 같은 작업의 호출이 계속 늘어날 수 있다.
**트레이드오프**: 등록 후 전송 전 종료도 보수적으로 1회를 사용한다. 일시 장애가 반복되면 결과를 완성하기 전에 멈출 수 있다 — 강의 자료는 처음부터 다시 만들기(ADR-034)가 출구다. 초기값은 현재 최대 생성 경로에서 도출했으며 실사용 적정성은 별도 검증한다. 호출 수 상한만으로 금액의 최대치를 보장하지 않는다.

### ADR-026: 입력은 구조 상한으로 묶고, 요청마다 UTF-8 바이트로 검사한다
**결정**: 재료마다 상한을 둔다(사용자 입력 글자 수 · 앞 단계 출력 상한 · 툴 결과 개수 · 개념 이름 50자 / 정의 200자 · 이름당 동명이의 후보 3개 · 개요가 참조하는 개념 20개). 단계별 **정적 최대 입력**(A/개요 16,000 · 본문 24,000 · 카드 25,000 · 임베딩 512 토큰)은 그 합으로 설계 때 계산해 비용 · 용량 계획에 쓴다. 요청마다는 직렬화한 요청 전체의 **UTF-8 바이트 수**를 단계 바이트 상한(토큰 목표의 4배, 잠정)과 비교해 넘으면 등록/전송 없이 `INPUT_TOO_LARGE`. 내용을 자동으로 자르거나 요약하지 않는다. ([03 §8.7](./03-generation.md))
**이유**: 호출 횟수와 출력 제한만으로는 입력 비용을 제한하지 못한다. 그런데 요청마다 정확한 토큰 수를 증명하려면 Chat Completions 에서 쓸 수 있는 방법이 없어 출시가 막혔다. 바이트 단위 BPE 에서는 토큰 하나가 최소 1바이트라 토큰 수 ≤ 바이트 수가 모델의 토크나이저 없이 성립한다 — 증명된 천장이다. 입력은 이미 구조적으로 묶여 있어 현실적 최대는 상한의 합으로 계산된다.
**트레이드오프**: 바이트 천장은 한국어에서 실제 토큰의 약 3~4배라 느슨하다 — 금액의 증명된 천장도 그만큼 느슨하고, 현실적 최대는 정적 합으로 따로 본다. 툴 정의 · 메시지 경계는 형식이 공개되지 않아 실측한 고정 여유분이며 원장의 실제 사용량 대조로 확인한다. 모델을 바꿀 때 바이트 단위 BPE 인지 확인해야 한다. 정적 합의 시스템 프롬프트 · 툴 스키마 크기는 구현 첫 작업에서 실측한다.

### ADR-027: 관련 숙련도는 주제/목적의 임베딩 검색과 키워드 검색으로 선별한다
**결정**: 생성 전 ‘주제 + 학습 목적’을 임베딩해 해당 사용자가 학습 완료한 개념 정의와 비교한다. 이름/정의 키워드 검색을 보완하고 ID별 순위를 합쳐 개수 · 입력 예산 안에서 숙련도를 주입한다. 전량 주입과 `R` 순 500개 제한을 제거한다. 검색용 임베딩도 원장 · 누적 몫에 포함하고 A의 임베딩 상한은 4회로 둔다. 임베딩 생성 실패는 키워드 검색만 사용한다. 선별/판정 근거는 같은 잡에서 재사용하고 커리큘럼 성공 시 보존한다. ([02 §5.4](./02-domain-data.md) · [03 §2 · §8.5](./03-generation.md))
**이유**: 학습 이력이 늘어도 이번 주제와 관련된 숙련도에 입력 예산을 쓸 수 있어야 한다. 검색 결과는 개념을 연결하거나 생략 여부를 직접 결정하는 근거가 아니므로 기존 동일성 · 숙련도 규칙과 분리한다.
**트레이드오프**: 임베딩 호출과 검색 로직이 추가되며 선수 개념 누락 · 동명이의 후보 · 넓은 주제의 검색 품질을 보장하지 않는다. 후보 수와 검색 임계값은 주제별 검증으로 정하고 버전으로 관리한다. 50개는 예시로 유지하며 개념 병합의 `0.46/0.78` 을 재사용하지 않는다. 구현 · 성과 검증은 아직 수행하지 않았다.

### ADR-028: 오류 신고와 카드별 복습 일시중지는 MVP에서 제외한다
**결정**: 사용자의 범위 결정에 따라 오류 신고 · 문제 카드의 복습 일시중지를 MVP에 추가하지 않는다. 신고 API/화면, 카드 중지 상태 및 집계 제외 규칙을 만들지 않는다. MVP 이후 필요성 · 범위를 사용자와 다시 결정한다. ([01 §6 · §7](./01-overview.md))
**이유**: 사용자가 해당 기능을 MVP 범위에서 제외하기로 선택했다.
**트레이드오프**: 잘못 생성된 카드를 사용자가 즉시 신고하거나 복습에서 제외하는 경로가 없다. 기존 공개 전 품질 채점은 유지하며, 이 제약을 알려진 한계로 기록한다.

### ADR-029: 개념 사전은 사용자별이다
**결정**: `concepts.user_id` 를 두고 매칭 · 조회 · 병합 · 쓰기 락을 그 사용자 범위로 한정한다. 탈퇴 때 `concepts` · `concept_match_logs` 를 함께 지운다. 임베딩 호출 수는 그대로다(새 카드의 정의마다 한 번). ([02 §5.2](./02-domain-data.md))
**이유**: 숙련도는 사용자 × 개념이라 다른 사용자의 개념에 연결해서 얻는 것이 없다. 전역 사전은 다른 사용자가 먼저 붙인 이름 때문에 `lookupMastery` 가 빗나가게 하고, 쓰기 스캔 · 락 · 병합 · 탈퇴 범위를 서비스 전체로 키운다. 데이터가 늘어날 것이라는 우려는 개념 행이 카드 하나당 최대 하나라 `flashcards` 행 수를 넘지 않고, 모든 조회가 사용자 범위라 테이블 전체 크기가 조회 속도를 정하지 않는다.
**트레이드오프**: 사용자끼리 겹치는 개념의 벡터를 중복 저장한다. 같은 표기 쌍이 갈리면 사용자마다 따로 병합한다 — 첫 방어선은 프롬프트의 표기 규칙([03 §6](./03-generation.md))이라 드물 것으로 보고, 반복되면 쌍 단위 묶음 병합 · 관리자 전역 동의어 표를 넣는다([01 §6](./01-overview.md)). 사용자 사이의 개념을 묶는 기능(예: 다른 학습자들이 어려워한 개념)이 생기면 그때 임베딩으로 묶는다.

### ADR-030: 판정 기록에 들어온 이름 · 정의를 남기고 별칭 조회 · 매칭에 쓴다
**결정**: `concept_match_logs` 에 `material_id` · `input_name` · `input_name_normalized` · `input_definition` 을 모든 분기에 남긴다. 그 개념에 연결 · 병합된 적 있는 이름을 별칭으로 써서 `lookupMastery` 는 별칭으로도 찾고, `resolveConcepts` 는 별칭을 이름 같음 분기(0.46)로 본다. 판정 기록은 임의로 지우지 않고, 병합은 행을 옮긴다. 커리큘럼 완전 삭제 때 해당 자료의 기록은 함께 삭제한다(ADR-035). ([02 §5.1 · §6.4 · §8.2.1](./02-domain-data.md))
**이유**: 연결되면 카드 단계가 낸 이름 · 정의가 버려져 ① 연결이 맞았는지 판단할 수 없어 임계값 재계산 표본이 치우치고 ② 잘못 합친 동명이의를 찾거나 되돌릴 수 없고 ③ 같은 개념을 다른 표기로 조회하면 `DETAIL` 로 빗나가 피드백 루프가 조용히 끊긴다. ③은 지표에 잡히지 않아 별도 표기 사전의 트리거가 오지 않는다. 매칭이 별칭을 보지 않으면 병합해도 같은 표기의 다음 카드가 다시 새 개념을 만들어 병합이 풀린다.
**트레이드오프**: 판정 기록이 감사 기록이면서 조회 · 매칭 경로가 되어 지우는 규칙이 엄격해진다. 별칭은 한 번이라도 연결된 표기만 잡고, 처음 보는 동의어는 여전히 못 잡는다. 잘못 연결된 별칭은 이후 같은 표기의 카드도 끌어오므로 U6 경계 판정에서 보고 되돌린다.

### ADR-031: 카드 단계는 개요의 개념 목록을 받고 `SKIP` 개념으로는 카드를 만들지 않는다
**결정**: ③ 입력에 본문과 함께 ①의 `masteryFindings` 중 학습자가 가진 개념의 이름 · 판정을 넣는다. 개념 자신의 판정이 `SKIP` 이면 그 개념으로 카드를 만들지 않고, 목록의 개념은 목록의 이름을 그대로 쓴다. 백엔드는 매칭 결과가 이번 `SKIP` 개념인 카드를 저장하지 않는다. ([03 §5](./03-generation.md))
**이유**: 본문만 보면 `SKIP` 개념의 한 줄 언급이 카드가 되고, 그 카드가 `minReviewCount` 를 0 으로 만들어 다음 강의에서 생략이 풀린다 — 아는 개념일수록 카드가 늘고 생략이 강의마다 풀린다. `minReviewCount` 규칙은 맞으므로 규칙이 아니라 카드의 출처를 막는다. 이름을 넘기면 카드 단계가 이 사용자 사전의 표기를 따른다.
**트레이드오프**: 카드가 10장보다 적을 수 있다. 지시를 어긴 카드에도 임베딩 호출 1회를 쓴다. 한 소절에서 `SKIP` 개념이 다른 개념과 함께 자세히 설명되어도 그 개념의 카드는 만들지 않는다.

### ADR-032: 잘못 합친 개념은 판정 기록으로 되돌린다 · jsonb 근거의 ID 는 고치지 않는다
**결정**: 연결(`LINKED`) 판정은 들어온 정의의 벡터(`input_embedding`)도 남긴다. 되돌리기는 그 판정의 이름 · 정의 · 벡터로 새 개념을 만들고, 고른 카드와 판정 기록 행을 옮긴다. 병합 · 되돌리기로 옮긴 판정 기록에는 `corrected_at` 을 찍는다. 둘 다 그 사용자의 진행 중 잡이 없을 때만 한다. 완료된 jsonb 근거는 생성 당시 스냅숏이라 고치지 않고 `concepts` 과 조인하지 않는다. ([02 §5.3 · §6.4](./02-domain-data.md))
**이유**: 벡터 없이 떼어 내면 새 개념이 비교에서 빠져 같은 실수가 반복된다. 판정 기록을 옮기지 않으면 잘못된 별칭이 다음 카드를 끌어온다. 사람이 고친 판정은 임계값 재계산에서 *실제로 틀린 판정* 의 라벨이 된다. 진행 중 잡은 카드 단계의 `SKIP` 검사가 개념 ID 로 비교하므로 옛 ID 와 어긋난다.
**트레이드오프**: 연결 판정마다 벡터를 하나 더 저장한다(카드 수 이하). 옮길 카드는 관리자가 눈으로 고른다 — 카드에 들어온 이름이 남지 않는다. 실패한 채 산출물이 남은 잡이 나중에 재시도되면 `SKIP` 검사를 한 번 빠져나갈 수 있다(카드 한 장).

### ADR-033: 유효한 강의 목록이 있고 생성 중이 아닐 때만 승인한다
**결정**: `DRAFT` · 활성 생성 잡 없음 · 검증을 통과해 저장된 강의 목록 있음을 승인 조건으로 삼는다. 그룹 단계의 상세 생성이 최초에 실패한 빈 초안은 승인할 수 없다(초기 잡 I 가 실패하면 커리큘럼 자체가 없다 — ADR-050). 다시 짜기가 실패해도 이전 성공 목록은 승인할 수 있고, 새 목록은 성공 트랜잭션에서만 교체한다. 승인과 적재/재시도/결과 저장을 같은 커리큘럼 잠금으로 직렬화하고, 승인 후 이전 실패 잡 재시도 및 목록 덮어쓰기를 막는다. ([02 §2 · §6.2](./02-domain-data.md) · [05 §2 · §4](./05-api.md))
**이유**: 강의가 없는 초안이 학습 중으로 전환되거나 승인한 목록이 뒤늦은 생성 작업으로 바뀌는 일을 막으면서, 실패한 다시 짜기 때문에 이전에 성공한 안까지 사용할 수 없게 되지 않도록 한다.
**트레이드오프**: 생성이 진행 중이면 이전 목록이 있어도 완료/실패까지 승인을 기다린다. 승인 이후 같은 커리큘럼의 다시 짜기는 기존 `DRAFT` 규칙에 따라 허용하지 않는다. 구현과 동시성 검증은 아직 수행하지 않았다.

### ADR-034: 실패한 강의는 사용자가 처음부터 다시 만든다 · 강의당 하루 2번
**결정**: 강의 자료 잡이 `JOB_CALL_LIMIT_EXCEEDED` · `INPUT_TOO_LARGE` 로 끝나면 사용자가 버튼으로 *처음부터 다시 만들기* 를 고를 수 있다 — 새 잡 행 · 새 호출 몫 · 1단계부터. 새 잡과 같은 검사(킬스위치 · 쿼터 · 진행 중 2개)를 받고 **강의당 하루 2번**(한국 날짜)까지다. 강의를 다시 열 때의 자동 재시도는 새 잡을 만들지 않는다. 그날 다 쓰면 `409 LESSON_RESTART_LIMIT` 이고 0시에 다시 열린다. U6 에는 자료 없이 두 코드로 실패한 채 남은 강의 수를 보인다. ([04 §4.9](./04-jobs-and-cost.md) · [05 §3.1](./05-api.md))
**이유**: 호출 상한은 한 작업의 호출이 끝없이 늘지 않게 하는 것인데, 출구가 없으면 장애 한 번으로 그 강의가 영원히 자료를 못 받는다 — 학습 완료 · 커리큘럼 완료가 막히고, 그룹이면 다음 단계까지 막힌다. 오류 신고가 없어(ADR-028) 사용자가 알릴 길도 없다. 장애 중 비용은 미확인으로 남아 쿼터에 잡히지 않으므로 새 몫에도 횟수 상한을 두되, 평생 횟수가 아니라 하루 횟수로 둬 막힘이 그날로 끝나게 한다(ADR-053).
**트레이드오프**: 처음부터 하므로 앞 단계 산출물(많아야 약 77원)을 버린다. 강의당 하루 최악 비용은 잡 상한의 2배(최초 잡을 만든 날은 3배)다. 장애가 여러 날 이어지면 날마다 새 몫이 생기고 그 비용은 미확인이라 쿼터에 안 잡힌다 — U6 의 미확인 호출 수와 실패한 채 남은 강의 수로 본다. 2번은 잠정값이다.

### ADR-035: 커리큘럼은 연결된 학습 기록 · 플래시카드와 함께 완전 삭제한다
**결정**: 사용자 결정에 따라 별도 그만두기/보관 상태를 없애고 `DELETE /curriculums/{id}` 로 완전 삭제한다. 검토 중 · 학습 중 · 완료 · 생성 중 모두 삭제할 수 있다. 커리큘럼의 강의/자료 · 플래시카드 · 카드 상태/복습 이력 · 자료의 개념 판정 기록 · 연결 잡을 한 트랜잭션으로 제거한다. 삭제 전에 이 범위와 복구 불가, 삭제한 학습 기록이 앞으로의 맞춤 학습에 반영되지 않음을 안내하고 확인받는다. 다른 커리큘럼의 카드/기록과 이미 발생한 생성 비용은 유지한다. ADR-017의 그만두기/초안 버리기 정책을 대체한다. ([02 §2 · §6.2](./02-domain-data.md) · [05 §2](./05-api.md) · [06 §2.7 · §8](./06-screens.md))
**이유**: 사용자가 삭제를 선택했을 때 커리큘럼과 연결된 학습 데이터가 함께 사라지는 일관된 동작을 제공하고, 그 결과를 확인 화면에서 명확히 알린다.
**트레이드오프**: 해당 카드의 누적 숙련도 근거와 해당 자료의 별칭/판정 표본도 사라진다. 다른 커리큘럼에 같은 개념의 학습 기록이 남아 있으면 그 기록으로 계산한다. 생성 중 삭제에는 적재/완료/복습과의 잠금 및 펜싱이 필요하며, 이미 등록/전송 중인 외부 요청의 과금까지 취소하지는 못한다. 늦은 응답은 사용량만 남기고 학습 데이터를 복원하지 않는다. 구현 · 검증은 아직 수행하지 않았다.

### ADR-036: 일일 복습 개수 제한을 두지 않는다
**결정**: 사용자 결정에 따라 하루 50장 제한을 제거한다. 첫 복습 카드와 기존 카드 모두 한국 날짜로 오늘까지 예정된 카드를 전부 제공하며, 오래 밀린 순으로 정렬한다. 사용자는 원하는 만큼 진행하고 중간에 나갈 수 있다. 평가 저장 · FSRS 다음 복습일 · 중복 제출 방지 규칙은 유지한다. 일일 허용량 응답/화면을 제거하고 커리큘럼 삭제 후 별도 당일 복습 카운터를 보존하지 않는다. ([02 §8.1](./02-domain-data.md) · [05 §6](./05-api.md) · [06 §11](./06-screens.md))
**이유**: 실사용으로 검증하지 않은 장수로 학습을 강제 종료하지 않는다. 복습은 저장된 카드/FSRS 상태를 처리하며 LLM을 추가 호출하지 않으므로 생성 비용 상한과 분리한다. 일일 제한을 없애 삭제 시 복습 한도용 집계를 유지할 필요도 없어진다.
**트레이드오프**: 밀린 카드가 많으면 목록과 세션이 길어질 수 있다. 현재 세션에는 조회한 목록을 고정하고 새 카드를 자동으로 추가하지 않으며, 사용자가 도중에 나가도 저장한 평가까지 유지한다. 개수 제한 제거만으로 미래 예정 카드를 미리 복습하거나 같은 카드를 즉시 반복하는 기능을 추가하지 않는다. 구현 · 검증은 아직 수행하지 않았다.

### ADR-037: 학습 완료 재요청은 성공으로 응답하고 복습 상태를 보존한다
**결정**: 강의 ID와 같은 커리큘럼 잠금으로 최초 완료를 한 번만 반영한다. 최초 완료의 강의 상태 · 카드 상태 생성 · 전 강의 완료 시 커리큘럼 전환을 한 트랜잭션으로 처리한다. 이미 완료한 강의에는 전체 커리큘럼 완료 후에도 `200` 을 반환하며 FSRS 상태/날짜 · 횟수/버전 · 복습 이력을 변경하지 않는다. 첫 복습 목록은 현재 그 강의의 미평가 카드만 반환한다. 삭제/소유권 없음은 `404` 다. ([02 §3](./02-domain-data.md) · [05 §3.2](./05-api.md))
**이유**: 완료 응답 유실이나 두 탭의 중복 요청이 복습 상태를 초기화하거나 충돌 오류를 일으키지 않도록 한다. 서로 다른 마지막 강의의 동시 완료에서도 커리큘럼 완료 전환을 놓치지 않는다.
**트레이드오프**: 완료 반영은 한 번이지만 응답 목록은 현재 상태에 따라 달라질 수 있다. 이미 첫 평가한 카드는 다시 첫 복습으로 보내지 않는다. 별도 요청 ID/응답 스냅샷을 저장하지 않는다. 구현 · 동시성 검증은 아직 수행하지 않았다.

### ADR-038: 이어 쓰기 후에도 잘린 본문은 실패로 처리한다
**결정**: 본문의 이어 쓰기는 최대 1회이며 섹션 수정과 단계 재요청 몫을 공유한다. 이어 쓰기 뒤에도 `MAX_TOKENS` 이면 `FAILED(LLM_OUTPUT_INVALID)` 로 끝낸다. 정상 종료와 필수 6섹션/내용 검증을 통과한 본문만 완료 단계로 저장하고 카드 생성으로 넘긴다. 잘린 자료/카드를 저장하거나 제공하지 않는다. 실패 후 명시적 사용자 재시도는 같은 잡에서 검증된 개요를 유지하고 본문부터 새로 생성하며, 이전 비용/누적 호출 상한은 유지한다. ([03 §4 · §7](./03-generation.md) · [04 §4.6](./04-jobs-and-cost.md))
**이유**: 핵심 설명이 빠진 본문으로 학습 완료와 플래시카드 생성이 진행되는 일을 막는다. 잘린 자료를 경고와 함께 제공하던 정책을 대체한다.
**트레이드오프**: 긴 강의의 생성 실패가 늘 수 있고, 재시도 시 본문 비용이 다시 발생한다. 정상 종료/섹션 검증이 자연어 설명의 정확성이나 충분함을 보장하지는 않으므로 기존 품질 채점은 유지한다. 구현 · 검증은 아직 수행하지 않았다.

### ADR-039: 카드 0장 전용 정책은 MVP에 추가하지 않는다
**결정**: 사용자의 선택에 따라 최소 1장 강제와 모든 개념이 이미 알려진 경우의 0장 예외 규칙을 추가하지 않는다. 최대 10장 · `SKIP` 개념의 카드 생성 금지 · 알려진 개념을 줄이고 모르는 개념의 심화에 분량을 쓰는 기존 기획을 유지한다. ([03 §2 · §5](./03-generation.md))
**이유**: 사용자는 기획대로 새로운/심화 내용을 채운다면 모든 내용이 이미 알려져 카드가 0장이 되는 경우는 드물 것으로 보고, 별도 예외 설계 없이 진행하기로 했다.
**트레이드오프**: 드물다는 판단은 구현 전 기대이며, 모델이 항상 기획을 지킨다는 보장은 아니다. 최소 카드 수로 생성 성공을 판정하지 않고 기존 콘텐츠 품질 채점으로 새로 배울 내용과 카드 품질을 검토한다.

### ADR-040: 공개 전 품질 표본의 치명 결함 허용치를 0개로 강화한다
**결정**: 사용자의 승인에 따라 검증 표본 강의 10개에서 치명 결함 0개를 요구한다. 기존 점수 평균 1.5 이상 · 항목별 평균 1.0 이상 조건도 함께 충족해야 한다. 사실/예시/모범 답안의 오류(K1~K3)는 평균 점수로 상쇄하지 않는다. 결함을 발견해 프롬프트 · 모델 · 생성/후처리 구성을 고친 뒤에는 새 표본 10개로 다시 검증하고, 이전 실패 결과도 보존한다. ([01 §9](./01-overview.md) · [07 §1.4](./07-testing.md))
**이유**: 공개 전 검사에서 이미 확인한 치명적인 오류를 1개까지 허용하던 기준을 없애고, 학습자가 틀린 설명/답을 학습할 가능성을 줄이도록 공개 기준을 명확히 한다.
**트레이드오프**: 재검증 비용과 공개까지 걸리는 시간이 늘 수 있다. 표본에서 오류가 없다는 결과가 이후 모든 생성 결과의 무오류를 보장하지는 않는다. 현재는 기준을 확정한 상태이며 실제 생성/채점 검증은 수행하지 않았다.

### ADR-041: 숙련도 미반영/반영의 효과 비교 실험은 우선 추가하지 않는다
**결정**: 사용자 선택에 따라 같은 주제/목적에서 숙련도 미반영/반영 생성 결과를 비교하는 개인화 효과 검증을 현재 계획에 넣지 않는다. 이미 확정한 숙련도 검색 방식 비교와 공개 전 콘텐츠 품질 게이트는 유지한다. ([07 §1.3 · §1.4](./07-testing.md))
**이유**: 사용자가 해당 비교 검증을 우선 추가하지 않기로 결정했다.
**트레이드오프**: 현재 검증 계획은 검색 관련성 · 콘텐츠 품질을 확인하며, 숙련도 반영 자체의 효과를 대조 결과로 측정하는 단계는 포함하지 않는다. 해당 실험을 수행하거나 효과가 입증됐다고 기록하지 않는다.

### ADR-042: DB 접근은 Spring Data JPA 하나 · 엔티티는 `infra` · Postgres 고유 기능은 네이티브 쿼리
**결정**: 도메인 테이블(`users` · `curriculums` · `lessons` · `materials` · `flashcards` · `reviews` …)은 JPA 엔티티로 다룬다. 엔티티는 `infra` 안에만 두고 리포지토리 포트는 트랜잭션 안에서 record 로 바꿔 돌려준다 — `core` 에는 `jakarta.persistence` 가 없다. `jobs` · `llm_calls` 쓰기와 Postgres 고유 기능(`SKIP LOCKED` · advisory lock · `ON CONFLICT` · `RETURNING` · 벡터 거리 · 숙련도 집계)은 `EntityManager` 네이티브 쿼리로 쓴다. 같은 트랜잭션에서 JPA 로 바꾼 행을 네이티브 쿼리로 읽기 전에 `flush()` 를 명시한다. ([04 §1 · §2 · §5](./04-jobs-and-cost.md))
**이유**: 기술 스택을 JPA 하나로 묶는다 — 국내 백엔드에서 주력으로 쓰는 방식이고, 네이티브로 남는 20개 안팎의 문장도 같은 `EntityManager` · 트랜잭션 안에서 돈다. MyBatis 는 강점인 동적 SQL · XML 분리 · 중첩 결과 매핑을 쓸 일이 없고(조건이 고정된 문장들) 프레임워크와 타입 핸들러(`vector` · `jsonb` · `text[]`)만 는다. `JdbcClient` 는 record 매핑이 간결하지만 접근 방식이 하나 더 생긴다. QueryDSL 은 JPA 위라 Postgres 고유 문법은 결국 네이티브로 빠진다.
**트레이드오프**: 네이티브 쿼리 결과를 record 로 받는 매핑이 `JdbcClient` 보다 번거롭다(결과 매핑 설정 · 인터페이스 프로젝션). 펜싱 · 원장 · 락처럼 틀리면 돈이 나가는 문장이 JPA 코드 사이에 섞이므로 네이티브임이 드러나게 둔다. 엔티티 ↔ record 매핑 코드가 는다. 동적 SQL 이 많아지면 MyBatis · jOOQ 를 다시 본다.

### ADR-043: MVP는 기간 없이 커리큘럼을 생성하고 학습 플랜은 후속 기능으로 둔다
**결정**: 사용자 결정에 따라 초기 입력은 주제 · 학습 목적만 받는다. 기간 · 주당 학습 가능 시간/학습량 입력, 예상 완료 기간, 주차별 일정과 일정 재조정은 MVP에서 제외하고 후속 학습 플랜 기능으로 둔다. 커리큘럼은 내용과 권장 순서만 제안하며 학습 시점 · 속도 · 실제 순서는 사용자가 선택한다. `curriculums.weeks` · `lessons.week` 및 해당 API/생성 출력/화면을 제거한다. 주당 3~5강 규칙과 1~8주 제한도 제거하며, 기존 총 40강 상한은 유지한다(검증된 목록 1~40강). 다시 짜기는 내용 · 범위 · 깊이 · 권장 순서를 조정하고 일정은 생성하지 않는다. FSRS 복습 일정은 유지한다. ([01 §5 · §6](./01-overview.md) · [02 §6.2](./02-domain-data.md) · [03 §2](./03-generation.md) · [05 §2](./05-api.md) · [06 §6 · §8](./06-screens.md))
**이유**: 사용자는 학습량/기간을 받아 일정을 정하는 기능을 커리큘럼과 별도인 학습 플랜으로 판단했다. MVP는 무엇을 어떤 순서로 배울지 제안하고, 학습 일정은 사용자가 자유롭게 정하도록 범위를 확정한다. 임의로 짧은 기간을 입력했을 때 내용이 압축되거나 해당 기간의 목표 달성을 약속하는 문제도 줄인다.
**트레이드오프**: MVP는 목표 완료 시점이나 주간 분량을 안내하지 않는다. 강의 수는 주제 · 목적 · 숙련도에 맞춰 정하되 상한을 채우려고 늘리지 않는다. 넓은 목표의 범위 적절성은 기존 콘텐츠 품질 채점에서 확인하며, 이번 결정만으로 어떤 주제든 40강 안에 충분히 담을 수 있다고 보장하지 않는다. 학습 플랜을 추가할 때는 시간 추정 기준과 범위/속도 조정 규칙을 별도로 결정한다. 구현 · 검증은 아직 수행하지 않았다. Q228의 `lessons.week` 추가 결정을 대체한다.

### ADR-044: 정상 종료는 진행 중인 외부 호출 하나를 끝내고 반납한다
**결정**: SIGTERM(배포)을 받으면 새 잡 수령을 멈추고, 각 실행기는 지금 하던 외부 호출이 끝날 때까지 기다려 사용량을 기록하고 그 호출로 단계가 끝났으면 산출물을 저장한 뒤 잡을 반납한다. 다음 호출 · 백오프 · 다음 단계는 시작하지 않는다. 기다림은 유예 120초 안에서만이고, 넘으면 즉시 반납한다. Spring 종료 대기(130초) · 프로세스 관리자의 강제 종료 대기(150초 이상)를 유예보다 길게 맞춘다. ([04 §4.5](./04-jobs-and-cost.md))
**이유**: 즉시 반납하면 진행 중 호출의 결과가 펜싱으로 버려지고 새 프로세스가 그 단계를 다시 한다 — 본문 단계라면 약 57원이 배포마다 실행기 수만큼 버려진다. 비싼 단계(잡 A · 본문 · 카드)는 대부분 호출 한 번으로 끝나므로 그 호출만 기다리면 결과를 살린다. 리스(5분)가 유예보다 길어 기다리는 동안 회수되지 않는다.
**트레이드오프**: 서버가 한 대라 배포 중 중단 시간이 하던 호출의 남은 시간만큼(최대 약 2분) 늘어난다. 개요의 중간 라운드나 이어 쓰기가 남은 본문처럼 단계가 끝나지 않은 호출은 여전히 버려진다. 바깥 대기 시간을 안 맞추면(Docker 기본 10초) 기다리는 도중 SIGKILL 로 죽어 리스 만료 회수 경로가 된다.

### ADR-045: 넓은 주제는 분할안을 제안하고 단계 완료 후 다음 커리큘럼을 생성한다
**결정**: 사용자 승인에 따라 넓은 목표는 여러 커리큘럼의 제목 · 범위 · 목적 · 선행 관계/순서를 먼저 제안한다. 1단계부터 사용자 클릭으로 상세 커리큘럼을 생성해 검토/승인/학습하고, 해당 단계의 모든 강의가 완료되면 U3 완료 화면과 U2에서 다음 단계 생성 버튼을 제공한다. 다음 단계의 상세 목록은 클릭 시 최신 숙련도로 만든다. 완료 직후 자동 생성하거나 모든 단계의 목록/자료를 미리 만들지 않는다. 분할안과 단계 연결은 서버에 보존하며 새로고침/다른 기기에서도 이어갈 수 있어야 한다. 같은 단계의 동시 요청은 기존 커리큘럼/잡으로 연결한다. 카드 복습 완료/특정 숙련도 달성을 다음 단계의 조건으로 더하지 않는다. 단계 안의 강의 순서와 독립 주제의 생성은 기존대로 자유다. ([06 §9](./06-screens.md) · [02 §2.1](./02-domain-data.md) · [05 §2.1](./05-api.md))
**이유**: 넓은 목표를 학습 가능한 단위로 나누면서 이전 커리큘럼을 마친 사용자가 다음 주제/목적을 다시 입력하지 않고 이어갈 수 있게 한다. 후속 상세 내용은 실제 생성 시점의 학습 기록으로 구성하고, 사용자가 진행할 때 생성 비용을 지출한다. 기간/일정을 배정하는 학습 플랜은 MVP 제외 상태로 유지한다.
**트레이드오프**: 분할안 보존/단계 연결/동시 생성 및 삭제 정책의 설계가 추가된다. 각 상세 커리큘럼의 1~40강 상한은 유지하며 분할안 생성의 잡/입출력 규약 · 단계 개수 상한 · 저장 스키마 · API 는 구현 전에 확정한다. 개별 단계 삭제 후 처리는 ADR-056 에서 정했다. 이번 승인은 분할과 순차 생성의 화면/동작 결정이며 이 확장 명세나 구현/검증이 완료됐다는 뜻은 아니다. 포트폴리오 기록 추가 승인은 포함하지 않는다.

### ADR-046: 커리큘럼 묶음과 단계를 분리하고 실제 커리큘럼을 필요할 때 연결한다
**결정**: 사용자가 승인한 커리큘럼 묶음의 모델을 `CurriculumGroup`/`curriculum_groups`, 단계별 분할안을 `CurriculumStep`/`curriculum_steps`으로 정한다. 묶음은 사용자와 전체 목표, 단계는 순서/제목/범위/생성용 주제·목적을 보존한다. 실제 `Curriculum`은 nullable·unique `step_id`로 연결하며 미생성 단계에는 빈 커리큘럼/강의/자료를 만들지 않는다. 독립 커리큘럼은 연결 없이 유지한다. 단계 순서는 묶음 안에서 unique이고, 묶음/단계의 학습 상태는 연결 커리큘럼/잡에서 조회한다. 초기 분할안은 초기 잡 I(`CURRICULUM_INITIAL`)의 성공 결과로 저장한다(ADR-050 — 처음 정했던 분할안 전용 잡 `CURRICULUM_GROUP` 을 대체했다). 탈퇴 삭제에 묶음/단계를 포함한다. ([02 §1 · §6.2.1 · §7](./02-domain-data.md) · [04 §4.2](./04-jobs-and-cost.md))
**이유**: 전체 목표와 아직 만들지 않은 단계의 계획을 실제 학습 내용/진도와 구분해 보존한다. 다음 단계 생성 시 저장된 입력과 최신 숙련도를 사용할 수 있고, 단계별 중복 생성은 DB 제약으로 막는다. 묶음/단계 상태를 따로 저장해 기존 학습 상태와 어긋나는 일을 피한다.
**트레이드오프**: 테이블 두 개, 단계 연결과 소유권/잠금/탈퇴 처리가 추가된다. 그룹 조회/단계 생성 API, 초기 잡 I 의 출력/입력/시간/누적 호출 상한은 후속 결정이다. 개별 단계 삭제 후 재생성/진행과 묶음 전체 삭제는 ADR-056 에서 정했다. FK는 연결된 커리큘럼을 부모 삭제로 자동 제거하지 않는다. 이후 ADR-050에서 초기 분할안 잡/대상과 빈 묶음 선생성을 입력을 먼저 보존하는 통합 잡으로 대체했다. 이번 반영은 문서 모델링이며 DB 마이그레이션/코드 구현/실제 DB 테스트는 아직 수행하지 않았다.

### ADR-047: 단일/그룹은 LLM이 판단한다
**결정**: 사용자 승인에 따라 LLM이 주제/학습 목적을 보고 단일 커리큘럼 또는 그룹을 제안한다. 하나의 일관된 목표인지, 독립적인 하위 목표와 선행 단계로 나누는 편이 적절한지를 기준으로 하고 강의 수만으로 분류하지 않는다. 단일이면 강의 목록, 그룹이면 분할안을 사용자가 검토하며 그룹의 각 상세 커리큘럼은 기존 순차 생성 규칙을 따른다. 서버는 유형/출력 구조/상한/순서를 검증한다. 그룹 화면은 ADR-054 에서 정했다(처음에 둔 그룹 UI 보류를 대체). ([03 §2.1](./03-generation.md) · [06 §9](./06-screens.md))
**이유**: 학습 목표의 의미와 선행 관계를 바탕으로 분할안을 제안하도록 한다.
**트레이드오프**: 의미 분할의 적절성은 구조 검증만으로 보장하지 않는다. 실제 결과는 기존 콘텐츠 수동 채점과 사용자 검토 대상이다. 당시 판단을 어느 호출/잡에 배치할지, 초기 API/출력 계약과 예산은 후속 설계로 남겼다. 판단/결과를 첫 생성 호출에 함께 넣는 배치는 ADR-049에서 확정했으며 잡 대상/접수/결과 연결은 ADR-050에서 확정했으며 정확한 출력/예산/그룹 추가 API는 후속 설계다. 단계별 학습 완료 후 다음 생성이라는 기능/모델 결정은 유지하며, 그룹 기능 전체를 MVP에서 제외한 결정으로 해석하지 않는다. 구현/검증은 아직 수행하지 않았다.

### ADR-048: 작업 성공·실패·회수는 상태 전환과 함께 이벤트로 기록한다
**결정**: 사용자 승인에 따라 `job_events`에 `SUCCEEDED` · `FAILED` · `RECLAIMED`를 기록한다. 성공/실패는 실행 권한 조건을 가진 잡 상태 전환이 1행을 바꾼 경우에만 같은 트랜잭션에서 이벤트를 삽입하며 성공 산출물도 함께 커밋한다. 회수는 만료된 `RUNNING`을 새 회차로 수령한 경우에만 수령 SQL에서 기록한다. 이벤트 기록 실패는 상태 전환까지 롤백하고, 재시도 적재/성공으로 이전 실패 이력을 덮어쓰지 않는다. 최근 24시간 실패율은 공통 DB 기준 시각의 창 안에서 `FAILED / (SUCCEEDED + FAILED)`로 계산하고 분모 0은 NULL로 제공한다. 삭제/탈퇴 시 잡 연결을 해제하되 사용자/콘텐츠 원문 없는 운영 사실은 남긴다. ([02 §6.9](./02-domain-data.md) · [04 §4.3 · §4.6 · §9](./04-jobs-and-cost.md) · [05 §7](./05-api.md))
**이유**: `jobs`의 현재 상태만으로는 재시도 전 실패나 리스 회수를 복원할 수 없다. 운영 프로세스 재시작에도 이력을 유지하고, 삭제가 과거 지표를 바꾸거나 이벤트 기록 실패로 지표와 작업 상태가 어긋나는 일을 막는다. 실패 후 재시도가 성공하면 실패/성공을 각각 1건으로 세므로 1/2이며 회수는 별도 집계한다.
**트레이드오프**: 테이블/인덱스와 상태 전환 시 추가 쓰기가 필요하다. 이 지표는 관측된 종결 실행의 실패 비율이며 고유 작업의 최종 실패율이나 서비스 가용성을 뜻하지 않는다. 최초 수령 · 정상 반납 뒤 수령 · 실패 잡 재시도는 회수로 세지 않고, 프로세스 종료를 가상의 실패 이벤트로 만들지 않는다. 이벤트에는 사용자/커리큘럼 ID나 오류 원문을 넣지 않는다. 구현 · DB 장애 테스트는 아직 수행하지 않았으며 검증 계획만 [07 §1](./07-testing.md)에 반영했다. 포트폴리오 기록 승인은 포함하지 않는다.

### ADR-049: 첫 생성 호출에서 단일/그룹 판단과 해당 결과를 함께 반환한다
**결정**: 사용자 승인에 따라 초기 생성의 첫 채팅 호출에서 단일/그룹 유형을 판단하고 단일이면 강의 목록, 그룹이면 단계별 분할안을 같은 응답으로 반환한다. 정상 생성 경로는 채팅 1회이며 판단용 호출을 따로 두지 않는다. 단일 결과를 받은 뒤 강의 목록을 만들거나 그룹 결과를 받은 뒤 분할안을 만들기 위한 추가 생성 호출도 두지 않는다. 그룹 단계의 상세 커리큘럼은 기존대로 사용자 클릭 시 생성한다. 초기 단일 결과의 숙련도 개인화 정책은 유지한다. ([03 §1 · §2.1](./03-generation.md) · [05 §2.1](./05-api.md))
**이유**: 판단과 생성에 같은 주제/목적을 따로 보내는 추가 호출을 줄이고, 반환한 유형과 그 결과를 함께 검증할 수 있게 한다. 초기 그룹 결과를 받았다고 모든 단계나 첫 단계의 상세 목록을 자동 생성하지 않는다.
**트레이드오프**: 한 호출이 두 결과 유형을 처리하므로 공통 입력/유형별 출력 스키마와 최대 크기, 모델/입력/출력/누적 호출/수정 규약을 함께 설계해야 한다. 당시 유형 확정 전 요청 저장/잡/API 결과 연결은 후속 결정으로 남겼으며 ADR-050에서 초기 잡 입력 보존/성공 시 생성으로 확정했다. 기존 단일 초안 또는 빈 묶음을 선생성하는 계약만으로 이 진입이 완성되지는 않는다. 검색 임베딩/전송 재시도/형식 수정은 별도 외부 시도이며 1회가 비용 상한이나 실제 지연 감소의 측정 결과를 뜻하지 않는다. ADR-047의 판단 호출 배치 미정 항목을 갱신하며 구현/실제 호출 검증은 아직 수행하지 않았다. 포트폴리오 기록 승인은 포함하지 않는다.

### ADR-050: 초기 입력은 잡에 보존하고 성공할 때 커리큘럼 또는 그룹을 만든다
**결정**: 사용자 승인에 따라 최초 주제/목적을 초기 잡 I(`CURRICULUM_INITIAL`)의 `payload.request`에 보존하고, 검증된 결과를 저장하는 성공 트랜잭션에서 실제 단일 커리큘럼 또는 그룹/전체 단계를 생성한다. 별도 요청 테이블이나 빈 단일/그룹을 선생성하지 않는다. 실패/반납/재시도는 같은 잡의 입력/선별/검증된 응답 체크포인트와 누적 호출 예산을 유지한다. 초기 잡은 성공 시 해당 결과 FK 하나에 연결하며 종류는 바꾸지 않는다. 접수는 `POST /curriculum-requests`의 `202 { jobId }`, 미완료 요청 조회와 잡 결과의 유형/ID로 복귀한다. ([04 §4.2](./04-jobs-and-cost.md) · [05 §2 · §4](./05-api.md) · [06 §7](./06-screens.md))
**이유**: 첫 생성 호출의 결과가 단일/그룹 어느 쪽인지 아직 모르는 시점에 잘못된 빈 리소스를 만들지 않는다. 작업 기록으로 대기/실패/재시작을 처리하고, 성공한 유형에 맞는 검토로 이동한다. 사용자에게는 성공 결과가 생긴 뒤 승인/학습 대상이 나타난다.
**트레이드오프**: 초기에는 커리큘럼 ID가 없으므로 잡 ID 기반 대기/복귀와 결과 연결 API가 필요하다. 성공 전/후의 FK CHECK가 다르며 첫 펜싱 UPDATE는 RUNNING 상태를 유지한 뒤 결과 삽입/성공/연결/이벤트를 같은 트랜잭션에 저장한다. 단일 결과 삭제는 연결 초기 잡도 지우고 탈퇴는 미완료 잡의 입력까지 지운다. 그룹의 단계 상세 생성은 대상이 이미 정해져 있으므로 기존 초안+잡 A 계약을 유지한다. ADR-046의 빈 묶음/전용 잡 G 모델과 초기 단일 빈 DRAFT 선생성은 이 초기 잡으로 대체한다. 최초 접수 중복 방지는 ADR-051, 실패한 요청 지우기는 ADR-055 에서 정했고 출력/예산/그룹 추가 API는 후속 결정이다. 구현/실제 DB 및 화면 검증은 아직 수행하지 않았으며 계획만 갱신했다. 포트폴리오 기록 승인은 포함하지 않는다.

### ADR-051: 초기 생성 요청은 요청 식별자로 중복 접수를 막는다
**결정**: 사용자 승인에 따라 화면이 초기 생성 요청마다 식별자를 만들고, 같은 요청 재전송에는 같은 식별자를 사용한다. 서버는 같은 사용자/식별자/내용에 기존 작업을 반환한다. 사용자가 새로 생성하면 같은 주제라도 새 식별자를 사용한다. 실패한 작업 반환과 명시적 재시도는 구분한다. ([05 §2](./05-api.md))
**이유**: 버튼 연타나 접수 응답 유실로 같은 유료 생성 작업이 중복되는 일을 막는다.
**트레이드오프**: 식별자 보존/내용 충돌/동시 접수/삭제 후 재전송의 구체적인 저장과 검증은 해당 TASK에서 설계한다. 삭제한 결과를 복원하지 않는 기존 원칙을 유지한다. 구현/검증은 아직 수행하지 않았다.

### ADR-052: 큰 흐름을 먼저 확정하고 세부 설계는 관련 TASK에서 한다
**결정**: 사용자 요청에 따라 사전 기획을 MVP 범위와 주요 사용자 흐름 중심으로 마무리한다. DB/API/경합/수치 등 세부 설계는 관련 TASK를 시작할 때 Codex가 문서화하고 구현/검증한다. 통상적인 구현 선택마다 사용자에게 확인을 요청하지 않는다. 기존 확정 제약은 유지하며 MVP 범위나 주요 사용자 동작을 바꾸는 결정은 사용자와 다시 논의한다. ([01 개요](./01-overview.md))
**이유**: 세부 기획 질문이 계속 늘어나 개발을 시작하지 못하는 상황을 끝낸다.
**트레이드오프**: 일부 명세는 해당 TASK에서 구체화된다. 문서의 ‘구현 전 확정’ 항목을 전체 개발 착수의 선결 조건으로 보지 않는다. 포트폴리오 기록의 별도 사용자 확인 규칙은 유지한다.

### ADR-053: 사용자가 고르는 다시 만들기는 평생 횟수가 아니라 하루 횟수로 묶는다
**결정**: 사용자 결정에 따라 커리큘럼 *다시 짜기* 는 커리큘럼당 하루 3회, 강의 자료 *처음부터 다시 만들기* 는 강의당 하루 2번(한국 날짜)으로 묶는다. 평생 횟수 상한은 두지 않는다. 횟수는 컬럼에 저장하지 않고 그날 적재된 잡 행에서 센다. 넘으면 `409 REGENERATION_LIMIT` · `409 LESSON_RESTART_LIMIT` 와 한국 자정까지의 `Retry-After`. 실패한 잡의 재시도는 같은 행이라 횟수를 쓰지 않는다. 처음부터 다시 만들기를 다 쓴 강의를 `nextLesson` 에서 건너뛰던 규칙은 없앤다 — 하루면 풀린다. ([02 §6.2](./02-domain-data.md) · [04 §4.9](./04-jobs-and-cost.md) · [05 §1.2 · §3.1](./05-api.md) · [06 §8 · §10 · §15](./06-screens.md))
**이유**: 평생 횟수를 다 쓰면 사용자에게 남는 길은 커리큘럼을 지우고 새로 만드는 것뿐이다. 그룹이 생긴 뒤로는 단계 커리큘럼을 지우면 단계 연결과 다음 단계 진행이 함께 흔들리므로 커리큘럼을 버리는 일을 줄여야 한다. 강의 자료는 평생 2번이면 장애 한 번으로 강의가 영원히 막히고, 커리큘럼이 완료되지 않아 그룹의 다음 단계까지 막혔다. 하루 횟수는 연타 · 장애 중의 브레이크는 유지하면서 막힘을 그날로 끝낸다.
**트레이드오프**: 한 커리큘럼 · 강의에 쓰는 총비용에 평생 상한이 없다 — 확인된 비용은 사용자 일일 쿼터가, 하루 몫은 횟수가 묶는다. 장애가 여러 날 이어지면 미확인 비용이 날마다 생길 수 있어 U6 의 미확인 호출 수로 본다. 다시 짜기 잡을 최초 생성 잡과 구별하는 방법은 해당 TASK 에서 정한다. 하루 3회 · 2번은 잠정값이다. 구현 · 검증은 아직 수행하지 않았다.

### ADR-054: 넓은 주제는 묶음 화면 하나로 다루고 초기 대기는 별도 화면에 둔다
**결정**: 사용자 결정에 따라 그룹은 묶음 화면 U11 하나로 다룬다 — 분할안 검토 · 단계 진행 · 다음 단계 만들기를 한 화면에서 하고, 단계 커리큘럼은 기존 U3 를 쓰되 위에 묶음 경로 한 줄을 붙인다. 홈에서 묶음은 한 항목이며 현재 단계(진행 중인 단계 중 가장 앞, 없으면 만들 수 있는 단계 중 가장 앞)만 보인다. 다음 단계 만들기는 홈 · U3 완료 · U11 에서 할 수 있고, 아직 아무 단계도 만들지 않은 묶음은 홈에서 바로 만들지 않고 U11 로 보낸다. 초기 생성 대기는 결과가 없는 동안의 별도 화면 U10 이며, 성공하면 결과 유형에 맞춰 U3 또는 U11 로 바꿔 넘어간다. ADR-047 에 있던 그룹 UI 보류를 대체한다. ([06 §6 · §7 · §9](./06-screens.md))
**이유**: 그룹 화면이 복잡해질 우려에 대해 새 화면은 하나로 줄이고, 학습 화면은 하나짜리 커리큘럼과 같게 둔다. 단계가 여럿이어도 다음 행동이 하나로 보이게 한다. 초기 생성이 성공하기 전에는 커리큘럼 · 묶음이 없어 U3 로 기다릴 수 없다.
**트레이드오프**: 사용자 화면이 10개로 는다. 묶음 조회가 단계마다 연결 커리큘럼의 상태 · 진도 · 다음 강의 · 활성 잡을 함께 돌려줘야 하며 그 계약은 [05 §2.1](./05-api.md) 에서 정한다. 분할안 다시 짜기 · 단계 편집은 여전히 없다. 화면 구현 · 검증은 아직 수행하지 않았다.

### ADR-055: 실패한 초기 요청만 사용자가 지운다
**결정**: 사용자 결정에 따라 `FAILED` 인 초기 잡 I 만 사용자가 지울 수 있다(홈 항목 · U10). 결과물이 없어 확인을 묻지 않는다. 짜는 중(`QUEUED` · `RUNNING`)인 요청은 지울 수 없다. 지우면 잡 행을 삭제하고 그 잡의 `llm_calls` 연결을 해제한다 — 쓴 비용은 원장에 남고 `job_events` 는 FK 로 연결만 풀린다. 다시 시도할 수 없는 실패는 지운 뒤 주제 · 목적을 채운 만들기 폼으로 보낸다(지우고 다시 쓰기). ([05 §2](./05-api.md) · [06 §6 · §7](./06-screens.md))
**이유**: 주제 거절처럼 다시 시도가 없는 실패 요청이 홈에 영원히 남지 않게 한다. 짜는 중인 요청은 수십 초면 끝나고, 이미 나간 호출은 되돌릴 수 없으며 생성 중 삭제의 경합만 늘린다.
**트레이드오프**: API 가 하나 는다. 짜는 중인 요청은 취소할 수 없다. 지운 요청의 재전송 처리(지운 것을 되살리지 않음)는 ADR-051 의 TASK 에서 함께 설계한다. 구현 · 검증은 아직 수행하지 않았다.

### ADR-056: 묶음 삭제와 단계 커리큘럼 개별 삭제를 제공한다
**결정**: 사용자 결정에 따라 묶음을 통째로 지울 수 있다 — 연결된 단계 커리큘럼마다 커리큘럼 완전 삭제(ADR-035)의 범위를 적용한 뒤 단계와 묶음을 한 트랜잭션으로 지운다. 단계 커리큘럼 하나도 기존 커리큘럼 삭제로 지울 수 있고, 그 단계는 미생성으로 돌아가 기존 생성 조건(1단계이거나 직전 단계 `COMPLETED`)으로 다시 만든다. 뒤 단계가 이미 있으면 그대로 둔다. 아직 아무 단계도 만들지 않은 묶음은 화면에서 *지우고 다시 쓰기* 로 안내한다. ([02 §2.1 · §6.2.1](./02-domain-data.md) · [05 §2.1](./05-api.md) · [06 §2.7 · §9](./06-screens.md))
**이유**: 분할안 다시 짜기가 범위 밖이라 분할이 마음에 들지 않을 때 빠져나갈 길이 필요하다. 한 단계만 다시 하고 싶을 때도 묶음 전체를 버리지 않게 한다. 새 진행 규칙 없이 기존 생성 조건으로 닫힌다.
**트레이드오프**: 묶음 삭제는 여러 커리큘럼의 잠금을 함께 잡는다 — 사용자 락 → 묶음 lock → 커리큘럼 lock(ID 오름차순) 순서이며 세부는 해당 TASK 에서 설계한다. 앞 단계를 지우면 그 단계를 다시 완료할 때까지 그 다음의 미생성 단계는 만들 수 없다. 묶음 삭제 API 의 이름과 응답은 [05 §2.1](./05-api.md) 에서 정한다. 구현 · 검증은 아직 수행하지 않았다.

### ADR-057: 숙련도 선별의 검색 설정은 공개 후 측정으로 확정한다
**결정**: 사용자 결정(2026-10-11)에 따라 검색 방식 비교(전량 주입 · 키워드 단독 · 임베딩 + 키워드)와 그 결과로 `selectionLimit` · `semanticMinSimilarity` · 숙련도 입력 예산을 확정하는 일을 공개 후에 한다. 그전까지 잡 I · A 는 잠정 설정 버전을 기동 설정에 명시해 쓰고, 측정으로 확정하면 버전을 올린다. ([02 §5.4](./02-domain-data.md) · [07 §1.3](./07-testing.md) · [SCHEDULE](./SCHEDULE.md))
**이유**: 라벨링에 6~8시간이 들고 공개 필수 목록에 없다. 공개 직후에는 사용자마다 학습한 개념이 적어 선별 방식의 차이가 작을 것으로 본다 — 측정하지 않은 추정이다.
**트레이드오프**: 공개 초기의 선별은 검증하지 않은 값에 기댄다. 관련 개념을 놓쳐 아는 내용을 다시 설명하거나 무관한 개념을 넣을 수 있다. 잠정값을 확정값 · 검증된 값으로 기록하지 않는다. 측정은 아직 수행하지 않았다.

### ADR-058: 개발 일정에 날짜를 붙이고, 밀리면 범위 대신 날짜를 옮긴다
**결정**: 사용자 결정(2026-10-11)에 따라 2026-10-12 ~ 11-30 의 7주 동안 공개 필수 목록 전부 · 운영 배포 · 품질 게이트 통과까지 마친다. 밀리면 범위를 지키고 날짜를 미룬다. 본인 실사용은 핵심 경로가 돌면 운영 서버(EC2)에서 시작한다. Q231(일정은 주차 대신 순서로)의 "다시 추정이 필요하면" 에 따라 날짜를 다시 붙인다 — 순서의 근거는 [01 §11](./01-overview.md) 그대로다. ([SCHEDULE](./SCHEDULE.md))
**이유**: 마감 목표가 생겼다. 운영 서버에서 일찍 쓰면 피드백 루프를 확인할 복습 데이터가 처음부터 운영 DB 에 쌓이고 배포 문제를 일찍 찾는다.
**트레이드오프**: 주 20시간 · 약 140시간에 추정 사용 시간이 약 110~125시간이라 여유가 적다. 운영 배포가 용량 측정보다 먼저라 Postgres 위치를 3주 차에 정한다 — 측정 뒤 바꾸면 데이터 이전이 필요하다. 가입 · 대기 명단보다 운영 배포가 먼저라, 그 사이 나 말고는 생성할 수 없게 하는 장치를 `1-auth` 에 둔다.

### ADR-059: Spring Boot 4 로 시작한다
**결정**: 사용자 결정(2026-10-12)에 따라 Spring Boot 4.x 최신 안정판으로 시작한다. 그동안 문서에 적은 "Spring Boot 3" 을 대체한다. 기본 패키지는 `com.mogum` 이다.
**이유**: 3.5.x 의 오픈소스 지원이 2026-06 에 끝났다(3.5.16 이 마지막 OSS 릴리스). 구글 OAuth 로 외부에 공개하는 서비스가 보안 패치 없는 버전에서 출발하면 공개 전후에 메이저 이전을 한 번 더 해야 한다. 코드가 없는 지금이 가장 싸다.
**트레이드오프**: Spring Framework 7 · Spring Security 7 · Jackson 3 · Hibernate 7 · Testcontainers 2 로 함께 바뀌어 예제와 구현 담당의 지식이 3.x 보다 적다 — 옛 API 를 쓴 구현이 리뷰에서 반려될 수 있다. starter 가 기능별로 쪼개졌다(Flyway 등은 전용 starter).
